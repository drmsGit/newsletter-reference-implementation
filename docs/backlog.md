- 🔴 **[Bug] — P1, and the sharpest finding in the review: a credential for brand A can fire brand B's mail.** **The permission is checked against one thing and the row is addressed by another.** `enforce_api_policy` verifies a brand-scoped permission against the declared `X-Brand` and writes that brand onto `request.state.current_brand` (`auth/dependencies.py:424-454`) — but `POST /delivery/send-instances/{id}/send` passes only the id (`delivery/router.py:133-143`) and `send_send_instance` loads the instance by id alone (`delivery/service.py:363-379`). An integration holding `sends.execute` on brand A sends `X-Brand: A`, names a send instance belonging to brand B, and the guard agrees. Unattended it mails immediately; gated it creates a held request branded A whose payload points at B, which an A approver then executes in good faith. The same shape runs through the whole by-id JSON write surface: `audience/router.py:60-95` (patch, delete, members), `campaigns/router.py:239-295` (the three PUTs added 2026-09-19), `content/router.py:95-141`. **Fix:** make the authorised brand a required argument of every brand-owned service mutation and put it in the same query that selects the target, walking the ownership chain (`module → variant → campaign → brand`, `group → brand`, `send_instance → brand`); a row outside the authorised brand is a 404, not a 403. **Why P1:** `tests/test_brand_scoping.py` proves isolation thoroughly at the data layer and not once by addressing a row by id over the API — so the layer a hand-crafted request reaches first is the untested one. Distinct from the `brand_id=None` list default below: that leaks reads, this one writes and sends. Source: `CODE_REVIEW_2026-09-19` P1-02, verified 2026-09-19.

- 🔴 **[Bug] — P1, and it defeats the guard whose own docstring explains why it must exist.** **The approval row lock is released by a commit made inside the action it is protecting.** `_claim` takes `with_for_update()` on the pending row (`approvals/service.py:162-175`) and `approve` means to hold it across `module.execute` (`:193-214`) — but the action runs on the **same session**, and `send_send_instance` sets the instance to `sending` and commits (`delivery/service.py:391-392`). That commit ends the transaction holding the lock while the pending row still reads `pending`, because `approve` writes its status only after execute returns (`:234-246`). Two approvers can therefore both claim and both enter execute; the second is stopped only by `send_send_instance`'s own status guard — which is precisely the masking `_claim`'s docstring names as the reason for its existence, now happening for real. The first approvable action that commits internally and is not independently idempotent will double-execute. **Fix:** claim by state, not by lock: `UPDATE pending_actions SET status='executing' WHERE id=? AND status='pending' RETURNING id`, run the action, then finalise only the claim this caller won. **Why P1:** concurrent approval is the guarantee the mechanism is sold on, and it is not there. Needs a two-session test where the action commits before returning. Source: `CODE_REVIEW_2026-09-19` P1-01, verified 2026-09-19.

- 🔴 **[Bug] — P1, and it is logged against a launch gate recorded as CLOSED.** **The sign-in enumeration oracle was not closed, it moved from the response body into the response latency.** Gate 4b's fix made every outcome return one unconditional 303 — known address, unknown address, deactivated user, failed send — and that discipline is thorough and stays. But `request_login_code` runs inline (`auth/router.py:93`): for a **known** address it supersedes outstanding codes, inserts a row, commits, and then calls the provider **synchronously** over HTTPS through `deliver_code`, while an **unknown** address returns after a single SELECT. With a real provider that is a several-hundred-millisecond difference in how long the identical 303 takes to arrive. **Fix:** queue the delivery, or floor the response time, so the two paths cost the same. **Why P1:** `docs/business/LAUNCH-GATES.md` records gate 4b as closed and the comment at `auth/router.py:77-79` says avoiding precisely this substitution was the point — a gate recorded as closed and not closed is worse than one recorded as open. Mock mail is the default, so the gap only opens with a real provider, which is the configuration public exposure uses. Source: [[Interview Prep - Auth, Permissions, Machine Principals]] → Q5.

- 🔴 **[Bug] — P2, the same defect family as the approval lock above and best fixed in one pass with it.** **The expiry sweep claims nothing.** `expire_due_pending_actions` selects every due row with no lock (`approvals/service.py:310-325`) and `_mark_expired` re-checks no status, takes no lock and commits unconditionally (`:297-307`). Two overlapping sweeps both emit `approval.expired` for the same row; worse, a sweep can read a pending row, an approver can decide it, and the sweep can then commit `status='expired'` over the decision from its stale ORM object — a request that was approved, executed and mailed, recorded as having lapsed. The docstring's "idempotent, and safe to run twice" is true sequentially and not concurrently, which is the distinction that matters once it runs on cron. **Fix:** `SELECT … FOR UPDATE SKIP LOCKED` plus a status re-check, or the same conditional `UPDATE … WHERE status='pending' RETURNING id` used for the approve claim; emit the audit event only for rows this worker actually transitioned. Source: `CODE_REVIEW_2026-09-19` P2-01, verified 2026-09-19.

- 🔴 **[Bug] — P2. A send can be permanently stuck in `sending` without anything having been sent.** **The status transition is committed before several fallible preflight steps, and outside the handler that would undo it.** `send_send_instance` commits `status='sending'` at `delivery/service.py:391-392`; the `try` whose handler marks the parent `failed` does not begin until `:508`. In between sits provider construction and capability validation (`:432-438`, `providers/factory.py:28-35`), which raises `ValueError` for an unsupported provider or an unsupported channel. If it does, the instance stays committed as `sending`, every later attempt is refused by the status guard (`:386-389`), and there is no route back. Through approvals it reads worse: `send_fire` treats a `ValueError` as a clean refusal (`approvals/actions/send_fire.py:143-149`), so the request is recorded `failed` while the send is wedged `sending` forever. **Fix:** do all non-mutating validation before the claim commit, or put everything after the claim inside the failure handler so every post-claim exception transitions the send out of `sending`. Source: `CODE_REVIEW_2026-09-19` P2-02, verified 2026-09-19.

- 🔴 **[Bug] — P2, and it is dormant: it arms itself the day the first subject-less action is registered.** **The partial unique index does not enforce "one open request per thing" when `subject_id` is NULL.** Postgres treats NULLs as distinct in a unique index, so two rows with the same `action_key`, `subject_type=NULL` and `subject_id=NULL` can both sit `pending` and the `IntegrityError` that `request_approval` relies on for idempotence (`approvals/service.py:128-139`) never fires. `subject_id` is nullable on purpose — `db_models.py:74-80` documents it as the ADR-142 §10 settings case — so the model explicitly supports exactly the shape the index silently stops covering, while the index comment claims "one open request per thing" without qualification (`db_models.py:119-137`). **Fix:** decide what identifies a subject-less request. Either uniqueness is per action when there is no subject (`NULLS NOT DISTINCT`, a coalesced expression index, or a second partial index for `subject_id IS NULL`), or subject-less actions carry a caller-supplied idempotency key — and then the action contract has to say so. Do it before the first such action exists, not after. Source: `CODE_REVIEW_2026-09-19` P2-03, verified 2026-09-19.

- 🔴 **[Bug] — P2, narrow and cheap.** **The six-digit login code is hashed with a bare unsalted sha256 — 10^6 of entropy, fully precomputable by anyone who can read the table, and identical codes collide across users.** `hash_secret` (`auth/service.py:61-62`) is one primitive serving four roles: session tokens, machine-credential secrets, rate-limit identifiers and `login_codes.code_hash`. - 🔴 **[Feature]** **Dev-data pseudonymization guard — a Mode-C safety property, not only a privacy one.** Decided 2026-07-31 (AI-layer interview, Cluster 4 / Q20b). **Problem:** the standard industry habit is copying production data into a "dev" environment — the user reports every company he has worked in or for ran exactly that *pseudo*-dev setup, which forces permanent caution inside the environment that exists so people *don't* have to be cautious. - 🔴 **[Feature] — Brand/theming structure across stages (note options now, implement in final MVP package).** Surfaced 2026-07-26. Goal: let each adopting company drop in their own styles so the whole architecture looks consistently *theirs*, across the (at least) two rendering stages — **web** (the Jinja management UI) and **email** (rendered newsletters). **Current state:** email is already the "drop a file" pattern — `storage/email_modules/brand.css` (~79 lines) is auto-inlined by the renderer and uses class names matching the module templates (`.module-headline`/`.module-button`/`.module-hero`…), with a header comment "replace per project". **Web has no brandable file** — it's raw Bootstrap 5 via CDN in `base.html`. There is **no shared source of truth** between the two, and **no preprocessor/build**. **Design answer to the questions raised:** (1) *One file for both stages is possible but a bad idea* — web and email have fundamentally different CSS capabilities (email = inlined, table-based, limited client support; web = full modern CSS), so a single stylesheet can't serve both cleanly. (2) *"Is there a CSS 'MJML'?"* — yes, the analogues are **CSS preprocessors** (Sass/SCSS, Less: variables, nesting, mixins, partials — write maintainable source, compile to targets) and **design tokens** (brand primitives — colors/fonts/spacing/radius — as the single source of truth, e.g. CSS custom properties, or a Style-Dictionary-style build that emits per-target files). Neither is "20,000 lines" — the point is a *small* token file + component partials. (3) **Recommended structure:** split **tokens** (what the brand *is* — a tiny file the company edits) from **stylesheets** (how tokens are applied per stage). One token source → two outputs: web consumes tokens via CSS custom properties (native support); email keeps a `brand.css` but its values come from the *same* tokens, **baked in as concrete values at build** (email clients don't support CSS variables reliably, so they must be inlined — which the renderer already does via `css_inline`). (4) *Separate files + a frontend to manage?* — a full in-app CSS editor is a footgun; better is a light **brand-tokens panel** (pick primary color / font / logo — manager-friendly, writes tokens, akin to the existing settings layer) while raw stylesheets stay files for developers. (5) **Consistency / no redundant classes** — the email side already enforces a shared `.module-*` class convention; extend the same discipline: one token source, a documented component-class vocabulary shared by both stages, component-scoped (not page-scoped) classes. **DECIDED direction (2026-07-26) — simpler than the tokens→two-outputs idea above; handle the two stages *differently*, no shared token pipeline:**
- **Email** keeps `brand.css` as a **separate, full-flexibility plain-CSS file** (developer/designer-owned, drives preview + MJML). Email is the stage managers actually care about visually — "I want rounded buttons, a shadow behind the box", etc. — so it gets **full raw-CSS control**, not a constrained token set. No abstraction forced on it.
- **Web** (management UI) gets a **small, simple brand-palette frontend** — **colors, fonts, sizes, logos only** (settings-layer style, applied to the UI via CSS custom properties). Deliberately *not* full CSS; keep it simple.
- Net: email = file + full flexibility; web = simple palette UI. No build step, no preprocessor. Consistency still comes from the shared `.module-*` class vocabulary on the email side and a small fixed token set on the web side.

**Scope (per working style):** lands in the final MVP package; the web palette is small and self-contained enough to build standalone earlier if wanted. Source: user, 2026-07-26.

- 📋 **Concurrent actors: a contention model, not just row locks.** **Promoted and broadened 2026-08-02** (`/interview-review`, AI Q4) from the earlier Features item "systemic pattern for concurrency guards", which was scoped to database write races and is superseded by this. - 📋 **Mode-A subject/preheader generation vs. decision-slot content — today's button only works for manually composed campaigns.** Surfaced 2026-08-02 (user, immediately after the first real Claude generation). **The problem.** [[ADR-141 — In-App Assistive AI Actions]]'s "suggest subject & preheader" reads the variant's module content and returns **3 options for a human to choose from**. That contract holds only while the campaign's content is *known and singular* at the moment the button is pressed — i.e. fully manual composition, or "at least one manual pick, show all". As soon as the campaign uses **decision slots** ([[ADR-083 — Personalization Happens Inside Variants Through Decision Slots]], including AI-driven selection) two things break. **(a) Timing** — the content does not exist until resolution has run, so the prompt has nothing real to read; the task can only run *after* resolution. **(b) Cardinality** — personalized resolution produces *many* renderings, each needing its **own** subject/preheader, so the task must emit **one pair per rendering** rather than three options for a human to choose between. Three suggestions × N renderings is not reviewable by a person, so the "human picks one" approval step that makes Mode A safe does not survive the jump — which puts this squarely against [[ADR-082 — AI May Recommend but Not Publish]] and needs an explicit decision rather than an implicit drift. **Options the user floated (recorded as options, not decisions).** *(A) A second, separately selectable action*, offered only once a campaign contains ≥1 decision slot. Because it is per-rendering it needs a **cost warning before it runs** — "run the decision engine now + prompt every rendering will cost ×N tokens", where N is the rendering count — and a **second warning if the manager later re-runs the decision engine**, since previously generated subject/preheader pairs may no longer match the content they were written for. *(B) Offer it only at schedule/trigger time* — the only moment at which "this **is** the content" is guaranteed. The manager accepts up front that the email ships AI-written subject lines unreviewed, softened by a "show results" view and a "cancel send" escape hatch. *(C) Leave the campaign-level button exactly as it is* — the 3-suggestion human-picks-one flow — but **scope its input to manually selected content only**, or at minimum to the campaign's selected categories, so it never silently produces a subject line for content that will be swapped out per recipient. (A/B/C are not mutually exclusive: C describes what the existing button should be narrowed to, whichever of A or B is added alongside it.) **Interactions to settle with it:** the per-rendering cost multiplier interacts with the spend cap ([[ADR-144 — AI Data and Model Governance]] §5) — a pre-call gate that today prices *one* call must price N; the "re-running decisions invalidates generated copy" problem is a dependency/staleness question the snapshot model may already have a place for; and the whole thing sits on top of the unresolved **resolution ordering + scope** item directly below, since "how many renderings are there" is exactly what that item hasn't decided yet. **Not written as an ADR deliberately** — the user's standing rule is that ADRs record *his* decisions, reached one question at a time through the interview process, so this is captured here as faithfully as possible and left for that conversation. Source: user, 2026-08-02 (post first real Claude generation).

  **Update 2026-08-02 — cost modelling, and a finding that reframes the question.** *(Same session; still not a decision — the user's read is that this "needs more thinking".)* **(1) The cost.** Distinct renderings are driven by slot combinatorics capped by audience size, **not** by recipient count. With 2000 content records across 40 categories (~50 candidates per category once a slot filters by category), distinct renderings ≈ `min(recipients, 50 ^ slots)`. At 1M recipients: 1 slot → 50 renderings (~$0.46); 2 → 2,500 (~$23); 3 → 125,000 (~$1,140); 4+ → capped at 1M (**~$9,100–12,000 for a single campaign**). Basis: the measured live run, ~700 in / 225 out on Opus 5 at $5/$25 per Mtok = $0.0091/call. **Two consequences for any warning UI:** it must count **distinct renderings, not recipients** (or it overstates by ~8× in the 3-slot case), and **dedupe-by-combination belongs in the design rather than as a later optimisation** — identical renderings take identical subject lines, and that alone is worth ~8× here. Cheaper model (~5×) and prompt caching (~12%) are the next two levers; note caching only starts paying at fan-out scale, unlike the single-campaign case where it was correctly skipped. **(2) The stronger finding is that cost is the *weaker* objection.** "Which of these 50 governed candidates suits a recipient scoring hiking 0.82 / wildlife 0.61" is a ranking problem over a vector that has already been computed — not a language problem. `recipient_top_score` answers it deterministically in microseconds, auditably, and A/B-testably; an LLM answering the same question costs ~1¢, is non-deterministic, resists clean A/B measurement, adds latency, and can hallucinate a content id. **At zero cost it would still be the weaker mechanism.** Industry shape appears to agree (public positioning, not verified internals): the large suites — Salesforce Einstein Content Selection, Adobe's equivalents — *do* select content per recipient at scale, using ranking/propensity models trained offline and scored at negligible marginal cost, and place *generative* AI at authoring with a human in the loop. That is the same split this architecture reached independently: **discriminative ML in the per-recipient path, generative AI at the edges.** So "they only build an email, not a personalized one" is not the explanation — they personalize per recipient, they just don't route it through a language model. **(3) Where the LLM does earn its place** — all off the per-recipient path: content **enrichment at ingest** (categories, tone, angle, summary — once per record, ~$10 for the whole 2000-record catalogue, and it improves every subsequent decision permanently — the highest-leverage item on this list); **authoring** (Mode A, human picks); **periodic outcome analysis** proposing strategy/weight changes (Mode B); and **explaining one decision** on demand (ADR-085). **(4) The user's own reframe:** move this out of campaign level and into the Mode-B analytic flow — *"check decisions + history and suggest updates to the algorithms"* — so **the AI touches the rules and the rules touch the recipients**. Costs a few dollars a month instead of thousands per campaign, and fits what is already decided ([[ADR-082 — AI May Recommend but Not Publish]], [[ADR-142 — Autonomous Workflows and the Automation Boundary]]'s orchestrator boundary) without amending either. **Refinement:** what should be ruled out is anything whose cost **scales with audience size** — a *campaign-scoped* analysis call ("this underperformed with segment X, what would you change?") is one call and cheap, so a blanket "no AI at campaign level" would be too broad. **(5) Sub-question that may deserve an ADR of its own: "AI" currently means two different things in this architecture.** [[ADR-080 — Human-governed Taxonomy Before AI Selection]] / [[ADR-081 — AI Ranks Within Governed Candidate Sets]] / ADR-082 are written model-agnostically — **ADR-081's "AI *ranks* within governed candidate sets" is fully satisfied by a gradient-boosted ranker and does not imply a language model** — while ADR-140–144 describe an LLM capability layer. Nothing currently states which kind belongs where, and that ambiguity is precisely what allowed an LLM to be costed into the per-recipient path in the first place. Stating it (*selection is learned ranking; generation is language*) would prevent the drift structurally instead of by remembering. **(6) Working conclusion to test, explicitly not yet decided:** the per-rendering generation option may not be "parked pending budget" but "shouldn't be built" — the comparison a buyer actually runs is not AI-personalization vs none, it is **LLM-per-recipient vs ranking-model-per-recipient**, and the latter wins on cost, latency, determinism *and* auditability simultaneously. That is a design without a case rather than a price to negotiate. Needs the interview before any of it goes into an ADR. Source: user + cost modelling, 2026-08-02.

- 📋 **Dynamic decision content × audience: resolution ordering + scope (build slot → suggest audience → run resolution?).** Surfaced 2026-07-26. When a campaign's content is *dynamic* (decision slots resolving per recipient, ADR-083), the plan-a-send flow has an unresolved ordering/scope question that the current build papers over. **(A) The circular dependency.** "Suggest audience" derives the audience *from* the campaign's content categories — `campaign_category_scores` (`audience/service.py`) reads module content records **plus already-resolved decision picks** (`DecisionResolutionDB.content_record_id`). But decision-slot content is chosen *per recipient*, so the content's categories depend on *who is in the audience* — which is the thing we're trying to suggest. Chicken-and-egg. Today it's masked: suggest-audience just reads whatever resolutions already exist (seeded/prior); for a fresh campaign whose content is *only* decision slots with no resolutions yet, it sees only the direct module content and ignores the slot's candidate pool entirely. **Candidate fix to break the loop:** suggest the audience from the slots' **candidate-pool** categories (the `candidate_filter.category_ids` + the categories of candidate content) rather than from already-resolved picks — i.e. target people interested in what the campaign *could* show, then resolve per person *within* that audience. **(B) Resolution scope — on segment / on every person / both?** Two scopes exist *implicitly* today via a strategy's `requires_recipient` meta (`decision/service.py`): personalized strategies (e.g. `recipient_top_score`) resolve **per recipient** (one row per (slot, recipient), new row only when the pick changes); non-personalized (e.g. `top_score`) resolve **once per slot** (recipient_id=NULL, single row updated in place). What does **not** exist is a first-class **per-segment** scope — "audience group A gets pick X, group B gets pick Y" as one resolution per segment rather than per individual. Options to decide: (i) per-person only (max personalization, but O(recipients) resolutions + the snapshot/storage cost already flagged in the rendered-HTML Needs-ADR item); (ii) per-segment (one resolution per audience group — far cheaper, coarser, loses individual personalization); (iii) both, selectable per slot (most flexible, most surface area). Interacts with the "freeze vs re-run at send" audience mode already built (`488c837`) and with batching (per-person resolution favors small batches; per-segment favors one blast). **(C) The meta-question the user is really asking: guide vs. implement.** Do we (1) document this as a **playbook guide** — "these are the steps: build slot → resolve → suggest audience → send, and here are the scope trade-offs" — leaving adopters to wire their own order/scope (max flexibility, fits the reference-architecture + playbook ethos, less turnkey); or (2) **implement** an opinionated codified flow in the product (a wizard-like build-audience → resolve → send path) that accepts **less flexibility** for a working out-of-the-box experience? Likely answer is a mix (a documented recommended flow + a sensible default implementation with escape hatches), but it needs deciding as an ADR before more of the plan-send/suggest-audience surface hardens around an unstated assumption. Ties to: ADR-083 (per-recipient decision personalization), the rendered-HTML/snapshot storage Needs-ADR item (per-person resolution multiplies stored artifacts), the batching/send-timing Needs-ADR item, and the freeze/re-run audience mode. Source: user, 2026-07-26 (Phase 3 audience/send session).

- 📋 **Bulk send: batching strategy + send-timing model — not designed yet, parked for later (don't answer now).** **Update 2026-08-07 (code review P2-04) — the review quantified the shape of the problem.** Per recipient the send path loads the recipient separately, executes every decision slot with its own queries and commits, renders HTML, makes **one blocking 15-second-timeout `httpx.post`**, and commits again. One worker thread can therefore sit occupied for a very long time, and a process restart leaves a half-sent batch with no idempotent recovery. The reviewer's recommendation matches the direction already sketched here and adds two pieces worth carrying into the design: move execution to a **worker/job boundary** rather than a request, and give retries **idempotent semantics** so a restart cannot double-send. Batch-loading recipients, reducing commits and bounded concurrency are the rest. Two linked open questions surfaced 2026-07-26 while reviewing the outbound Resend adapter (interview-prep Q8). **(1) Batching.** Today `send_send_instance` (`delivery/service.py:185-232`) does **one `provider.send()` call per recipient** in a serial synchronous loop (15s-timeout `httpx.post` each), so a real send is O(N × latency) wall-clock. This is fine at demo scale (~40 recipients) but doesn't scale. Open question: send per-recipient vs. in packages (e.g. batches of ~1000) — note that per-recipient rendering (decision-slot personalization, ADR-083) does **not** block batching, since Resend's batch endpoint (`POST /emails/batch`) accepts N *already-rendered* distinct emails; we'd render the batch then submit it as one call. Provider-capability-dependent (ADR-101) — not every provider has a batch API, so the `DeliveryProvider` contract would need an optional batch capability with a per-recipient fallback. Also relates to the async/concurrency direction (a bounded-concurrency `httpx.AsyncClient` is the other way to kill the O(N×latency) cost). **(2) Send timing — how do managers decide *when* a send goes out?** Range of models to think through, not decide now: (a) the classic fixed calendar slot a manager picks ("this Thursday 9:00"); (b) system-chosen optimal time per recipient (send-time optimization — the content is dynamic, so the *time* could be dynamic too); (c) a hybrid where **specific field/content types carry their own cadence** — e.g. a "news" module that must go "every Sunday" regardless of the recipient-optimal time, so a single send may have both fixed-cadence and dynamically-timed components. These interact: send-time-optimization implies many small per-recipient sends (favoring per-recipient calls or small batches), while a fixed calendar blast favors one large batch. No decision needed now — captured so batching and scheduling get designed together rather than separately. Source: user, 2026-07-26 (post-Resend-outbound, interview-prep Q8).

- 📋 **Finalize the rendered-HTML/snapshot storage strategy — now more urgent given per-recipient personalization.** **Update 2026-08-07 (code review P1-04, P2-06) — the review found something sharper than a storage question: the snapshot is described as the immutable final state but is not what gets sent.** `send_send_instance()` reads only `snapshot.variant_id` and then **re-renders from current database state for every recipient** — it never sends the stored HTML. - 📋 **Should hero / CTA (and any future module type) draw from the content catalogue like cms modules do?** Surfaced 2026-07-31 (user), while reviewing why a test hardcoded the field `headline` — a `hero` field that does not exist on cms modules, which use `headline_medium`. **Today:** cms modules (img_left/img_right) bind a `content_record_id`, so their copy is catalogue content — categorised, versioned, overridable, attributable. `hero` and `cta` are typically filled from raw `module_data` instead, so their copy lives nowhere in the catalogue. Modules *can* already reference content records regardless of type, so the gap is convention plus per-type field naming, not a missing capability. **Why it may be worth changing — the strongest driver is AI, not tidiness:** a company that will not let AI *write* content but will let it *assemble* a campaign (consistent with [[ADR-082 — AI May Recommend but Not Publish]]) needs **every slot to be selectable from the governed catalogue**. While hero and CTA sit outside it, a "fully AI-composed campaign" is impossible by construction — there will always be human-authored holes the decision engine cannot fill. Same argument extends the decision engine itself: it could pick a hero or a CTA, not only body modules. **Secondary benefits:** consistent field naming across manifests; click attribution on hero/CTA (the DOI/cold-start item above already needs fixed content linked to content records, and this generalises it); categorisation stays optional (a record with no category assignments simply never wins a category-driven pick). **Refinement (user, 2026-07-31) — the hard case is not CTA, and existing ADRs mostly draw the line already.** **A CTA always links to something specific**: it pulls its text from the linked content record, and where that text does not fit the context the manager uses the **override** function (exactly what [[ADR-040 — Introduce Override Layer]]/[[ADR-041 — Override Precedence]] exist for). Even a bare "visit our homepage" could be one general catalogue piece — and in practice there is always some context to link with. Hero behaves the same way. **The genuinely tricky case is a standalone headline module used to separate parts of an email** ("Deals", "This week") — it carries no message and no angle.
  That case is already answered by the ADRs, and in the opposite direction: [[ADR-012 — Content Records Represent Communication Units]] says a content record is a *communication unit — a specific message or content angle*, which a section divider is not; and [[ADR-031 — Newsletter Composition Stores Structure Not Content]] says composition owns *structural assembly*. So **a divider headline correctly stays in `module_data`; it is structure, not content.**
  **This also dissolves the AI capability ceiling above:** AI fills every *content* slot from the catalogue, while structural slots come from the composition/template and were never its job — so a fully AI-assembled campaign stays possible without putting dividers in the catalogue.
  **The [[ADR-011 — Store Reusable Content Only]] tension is therefore smaller than first assumed** — a hero or CTA promoting a specific thing is a communication unit even when used once.

- 📋 **Transactional sends — consent model, sending reputation, and whether they reuse the email modules.** Surfaced 2026-07-31 (user). The architecture today only does *marketing* communication: every send passes the consent floor (`CONSENTING_STATUS = "opted_in"`), and content comes from the governed catalogue. Transactional mail (order confirmations, password resets, booking details, masterclass signups) breaks all three assumptions at once, and **this may be a dealbreaker rather than a nice-to-have** — "why adopt a new system if it only handles marketing?" Three linked questions, none decided:

  **(a) Consent.** Transactional mail goes to people *without* marketing opt-in, by design. Does the model need **two distinct permissions** (marketing consent vs. a transactional/legitimate-interest basis) rather than the single `consent_status` gate in [[ADR-122 — Minimal Consent Model Required]]? Note the hazard already recorded in `docs/playbook-strategy.md` (Decision Log 2026-07-11, item 4): **some providers, e.g. Selligent, ignore opt-outs entirely on API-triggered sends because they classify them as transactional** — so "the provider will sort it out" is exactly the assumption this architecture exists to avoid. Also to settle: hard bounce / spam-complaint suppression almost certainly must still apply to transactional (a dead address is dead either way), while a *marketing* opt-out must not block a password reset — meaning the suppression gate and the consent gate are not the same gate. Interacts with the suppression/opt-out data-model item below.

  **(b) Sending reputation — and it is a THREE-way split, not two.** *Corrected 2026-08-02 (user), after sign-in codes made the third category concrete.* Marketing and transactional should not share reputation: complaint rates on marketing degrade delivery of mail people actually need. But **system-internal** mail — to the company's own operators, not to customers — is a third category again, and must not ride on transactional either. Its failure mode is unique and circular: if transactional delivery degrades a customer misses a receipt, but if system delivery degrades **nobody can sign in, including the person who would fix whatever caused it**. Transactional volume and complaint exposure are still customer-driven and outside the company's control, so sharing with it reintroduces the risk. So: **marketing customer / transactional customer / system internal**, three senders. Options per stream: a **separate provider**, or at minimum a **separate verified domain or subdomain**. The provider layer is already an adapter ([[ADR-100 — Provider Layer as Send and Feedback Adapter]]) and from-address is selectable per send, so the seam exists; what is undecided is whether "which stream a send belongs to" becomes a first-class concept rather than a manual from-address choice. See the system-mail channel Feature for the third stream, which now has running code.

  **(c) Do transactional emails reuse the existing modules, or get their own?** The real fork, because it decides how variables work:
  - **Reuse the marketing modules** — **PRO:** far less work, one module library, one rendering path. **CON:** needs a **global variable solution that is not limited to catalogue fields** — a transactional payload arrives as arbitrary JSON from an external system (order number, seat row, reset link), so rendering must interpret JSON directly rather than resolve content records. That is a genuine extension of the merge-context concept in [[ADR-005 — Separate Snapshot State from Recipient Delivery Artifact]], not a small addition.
  - **Dedicated transactional modules** — **PRO:** variables become straightforward, since a module is written against a known payload shape. **CON:** you need **a module per email type** (each has different fields), and you **cannot combine JSON payload + catalogue content** in one email — which matters if you want the decision engine to add recommendations for a recipient who *does* have marketing opt-in.

  **Open sub-question:** should a transactional email to an **opted-in** recipient be allowed to carry decision-engine recommendations? Tempting (high open rates), but it mixes streams and risks the reputation separation in (b). Plausible answer is **"we deliberately don't do this"** — while noting an adopting company may want it anyway, so the honest question is whether they can **integrate it themselves at a documented seam** rather than whether we ship it.

  **Timing:** potentially a stage-2 feature, but flagged as a possible dealbreaker for adoption, so the ADR should at least establish the *direction* (especially the consent model in (a), which is hard to retrofit) even if the build waits. Ties to: [[ADR-122 — Minimal Consent Model Required]], [[ADR-004 — Privacy Operations as a First-Class Architectural Concern]], [[ADR-005 — Separate Snapshot State from Recipient Delivery Artifact]], [[ADR-100 — Provider Layer as Send and Feedback Adapter]], [[ADR-131 — Email Module Templates Use MJML as Source Format]], and the suppression item below. Source: user, 2026-07-31.

- 📋 **Recipient suppression + opt-out reason model — "why is this person not getting communication?" as one auditable concept.** Surfaced 2026-07-31 (AI-layer interview, Cluster 3 / Q16). Cluster 3 (Mode B automation) only needs the *interface* — flows and external systems can **read, write and explicitly override** a suppression gate — and that part is settled in the Mode B ADR. What is **not** decided, and belongs here as a **data-model ADR rather than an AI one**, is the concrete shape. **Agreed direction:** a single **`suppressed_until`-style recipient-level gate** (one place, not several tables/fields), checked at audience resolution **beside the consent floor**, always paired with a **log recording *why*** — the log is the point, not an optional extra. Deliberately covers more than fatigue: **fatigue** (system-set, short), **a manual or AI decision** ("recipient is in cycle XXX, shouldn't get any emails" — especially useful for **reactivation** cycles), and recipient-set **pause/snooze** (§M2). **Ruled out during the interview:** modeling it as a `consent_status` value (a platform-only value would register as CRM divergence in `detect_consent_drift` — the same reason `suppress_recipient` deliberately skips `ConsentSyncLogDB`), and modeling it as an audience exclude rule-block (rule-blocks are per-*audience*; suppression is a property of *the person* and must hold across every campaign). **Three-tier precedence agreed:** (1) **consent** = hard floor, never overridable; (2) **suppression** = *soft* — not easy to overwrite but overridable by an explicit, logged act (the existing pin mechanism in `resolve_audience`, `… ∪ pins`, now also callable by external systems — e.g. a website form firing "this recipient must get the masterclass mail"); (3) include/exclude rule-blocks = normal audience logic. **Still to decide in this ADR:** (a) the concrete table/field shape, and whether the "why" log is its own table or an extension of the Mode-B action/audit log; (b) an **opt-out code / reason taxonomy** covering "opt-out because bounce / active unsubscribe / block / …" — note the **GDPR-block case is just a general opt-out**, with the GDPR information itself owned by the **CRM** ([[ADR-120 — CRM as Customer Source of Truth]] / [[ADR-122 — Minimal Consent Model Required]]), so the platform stores the *code*, not the legal record; (c) how a **cycle-scoped** suppression ("while in cycle XXX") is modeled, given it has no known end date and doesn't map onto a plain `until` timestamp. Ties to: [[ADR-122 — Minimal Consent Model Required]], `suppress_recipient` (`recipients/service.py`), the audience consent floor in `resolve_audience`, and the pause/snooze concept in `docs/business-interview-baseline.md` §M2. Source: user, 2026-07-31 (AI-layer interview, Cluster 3 Q16).

- 📋 **General data lifecycle / deletion & retention policy — not designed at all yet.** Confirmed during the interview review: the project has no deletion/cleanup story anywhere. Two concrete instances found so far, both symptoms of the same missing policy:
  - **Category/content record deletion vs. archival.** Categories accumulate historical value via preference/engagement scoring (`ContentCategoryAssignmentDB.score`, `RecipientPreferenceDB`) — hard-deleting a category breaks the ability to interpret that historical data (what a past engagement signal even meant). Leaning toward: never hard-delete a category/content record that has any historical usage — **archive** instead. An archived category stops contributing to *new* preference scoring; existing preference influence from it decays naturally over time (same mechanism as the not-yet-built Phase 3C signal decay, [[ADR-112 — Signals Use Time-Based Decay]]) rather than being force-zeroed. Only once a category is fully unused *and* decayed out would actual deletion become safe to consider.
  - **Snapshot lifecycle.** No uniqueness/idempotency key on snapshot creation means unbounded accumulation of near-duplicate snapshots per variant/recipient — consistent with "immutable append-only history" (ADR-061) but with no TTL, retention rule, or delete endpoint at all.

  Needs a dedicated ADR (none exists today) covering deletion/retention policy generally — likely also relevant to other accumulating tables (engagement events, decision resolutions, preference logs) once they're examined the same way. Tightly coupled to the Phase 3C signal layer design already flagged as open in `docs/playbook-strategy.md` §7. Source: [[Interview Prep - Content, Campaigns, Audience]] → Content Q6 (addendum); [[Interview Prep - Snapshots, Rendering, Email Modules]] → Snapshots Q6.
