# Backlog — Action Items from Interview-Prep Reviews

Granular, prioritized queue of concrete fixes/features decided while working through [[MOC - Interview Prep Baseline]] via the `/interview-review` command. Distinct from the phase-level roadmap in `docs/playbook-strategy.md` §6 (Phase 1-4, strategic/product sequencing) — this is the tactical "what do we act on, in what order" list.

Order within each section is priority order: **top = do next.** New items are inserted at the position matching their priority, not appended to the bottom. Bugs outrank features of similar importance.

## Bugs

- 🔴 **[Bug] — low severity.** **The AI suggestion UI withholds what the system already knows: truncation, and lost options.** Surfaced 2026-08-02 (`/interview-review`, AI Q8). Both underlying paths are handled correctly — a `max_tokens` stop is recorded in the audit row as "output hit its ceiling and is truncated" (`service.py:223-227`), and `parse_options` degrades to fewer options rather than raising (`subject_preheader.py:74-98`). **Neither reaches the manager.** (1) The campaign page renders the parsed options and the token count, but not the truncation message — so a manager sees three suggestions with no sign the third may be cut off mid-sentence, and applies one to a real campaign. (2) If the model returns two well-formed options instead of three, two are shown and nothing says one was lost. **Filed as a Bug rather than a Feature because in both cases the information exists and is deliberately withheld from the person acting on it** — the fix is to surface `AIRunDB.message` alongside the options, and to note when fewer options parsed than the prompt requested. Low severity: a truncated *subject line* is short enough that a manager would probably notice, and nothing is committed without a human clicking "Use this". Source: [[Interview Prep - AI]] → AI Layer Q8.

## Features

- 🔴 **[Feature]** Provider choice + real send on the **campaign send** flow (prepare-send → delivery). Today `send_instance_create` hardcodes `provider="mock"`, so the campaign "Trigger send" never sends real email — only the standalone **Send test** page (`/ui/send-test`, done) does. Add a provider selector (mock/resend) to the send-instance creation, and — before enabling a real campaign send — a **guardrail so it can't blast all recipients by accident** (e.g. a max-recipients cap or an explicit confirm; the demo has 40 recipients and the Resend free tier is 3,000/mo). Also the natural place to finally test the **multi-recipient real send** (3 recipients is enough to prove it). A note banner already points users to Send test from the delivery detail page. Source: user, 2026-07-26 (post-Resend-outbound). **Second reason to build this (2026-07-31, AI-layer interview Cluster 4 / Q19):** this guardrail is also a **Mode-C (AI-assisted development) containment measure**, not just accident prevention. DEV/PROD environment separation does **not** contain outbound email — as long as a DEV environment holds a working send-provider key (which development and testing require), an AI-made change in DEV can still deliver real mail to real people. The mock-provider default, the recipient cap and this guardrail are therefore the *actual* blast-radius limit for Mode C, and should be documented as safety properties rather than as dev conveniences.

- 🔴 **[Feature]** New idea, not yet designed: cost/token feedback before running an AI-driven decision batch — as decisioning increasingly routes through paid AI models or automation platforms (e.g. n8n), surface expected cost/token usage before committing to a run, for the recipients who *will* receive something (separate from the consent gate above, which is about not running decisioning for people who won't). Ties into the pluggable AI-capability extension points from the E1 resolution and the not-yet-built Phase 3C/3D AI work. Source: `docs/business-interview-baseline.md` §M3 (via `/business-review`).

- 🔴 **[Feature]** Small defensive safety-net check: refuse/alert if a fully rendered email ends up with literally zero content modules before sending — purely to catch accidental misconfiguration (e.g. every module in a variant is decision-slot-driven and all happened to resolve to nothing), not a business-policy decision. Confirmed the composition model (static content blocks) and strategy-plugin system already let a company guarantee content by construction if they want to — this is just a cheap guard against the accidental case, lowest priority. Source: `docs/business-interview-baseline.md` §E3 (via `/business-review`).

- 🔴 **[Feature]** **Required before public launch** (confirmed via `/business-review`, `docs/business-interview-baseline.md` §H1) — a real provider integration proves the "no vendor lock-in" pitch is real, not just a design promise; deliberately sequenced late (after remaining frontend work) since it costs real money. Also depends on this adapter layer existing first. Complete the inbound provider adapter layer (`providers/adapters/`, currently an empty mock file) — build the actual translation contract (e.g. an abstract base analogous to `DeliveryProvider` for outbound sends) that turns a raw provider webhook payload into the canonical `ProviderEventCreate` shape, since `ingest_provider_event` today just accepts an already-normalized payload directly with no real adapter behind it. Fits the "architecture + one worked example" strategy (per the provider-plugin-strategy decision in project memory) — this is the generic interface/contract any future custom connector would implement, not a vendor-specific plugin, so it doesn't conflict with the earlier decision to not ship maintained ESP/CRM plugins. **Must also own event-type normalization**: `event_type` is currently unconstrained free text with only a hardcoded `"click"` check giving it any meaning downstream (`insight/service.py`'s `EVENT_PREFERENCE_DELTAS`) — bounce/complaint (mandatory per ADR-106) are accepted into storage but never actually handled. Validation/normalization must be centralized in the adapter layer, not a single hardcoded enum, since the raw event-type vocabulary differs per provider (e.g. one ESP's `"hard_bounce"` and another's `"permanent_failure"` both need to normalize to the same canonical internal type). **Concrete reaction to bounce/complaint, now that the consent gate is resolved (see the consent-gate Feature above, from `docs/business-interview-baseline.md` §F1):** a bounce/complaint event should (1) update the recipient's `consent_status` (revoke/mark opted-out) and relay back to the CRM if there's no direct CRM↔provider webhook connection, since this platform is the only place positioned to notice; and (2) separately feed the Insight layer as a content-quality signal ("this content triggered a lot of complaints") — a distinct, analytics-flavored reaction to the same event, not the same action as the consent update. **Design approach, when this work starts:** favor (b) "fairly simple to adjust to your provider" over (a) "one contract that auto-fits every ESP generically" — real webhook payloads have enough genuine quirks (auth/signature schemes, batch-vs-single-event delivery, inconsistent field naming) that a fully generic auto-detecting layer would be over-engineering and fragile. Same pattern as the outbound side: a small, clean canonical contract (a `ProviderAdapter` interface mirroring `DeliveryProvider`) plus one well-documented worked example. Before finalizing the canonical event shape, pull real webhook API docs from a small, deliberately varied set of providers (not guess from memory, which may be stale) — suggested: one already referenced in the ADRs (Brevo or Resend), one classic/well-documented one (Mailgun or Postmark), and SES given it's common infrastructure for the target buyer. Enough variety to find genuine common ground without over-researching providers that'll never be used. Source: [[Interview Prep - Delivery, Providers, Recipients]] → Providers Q1, Q4; `docs/business-interview-baseline.md` §F2, §H1 (via `/business-review`).

- 🔴 **[Feature]** **Rework seed/demo content into realistic material — prerequisite for testing Mode A.** Surfaced 2026-07-31 (user). Today's seed content records are placeholders along the lines of *"this is content about X"* — fine for exercising plumbing, **useless for evaluating an AI feature**: a subject-line or content-suggestion task fed placeholder text produces generic output, so a test would be a **false negative** (concluding the feature doesn't work when the input simply carries no signal). Needs: real headlines and body text, realistic length, and enough **category variety** that personalization differences are visible between recipients. Keep the existing outdoor / hiking / wildlife theme so the demo narrative stays coherent. **Two payoffs:** it unblocks meaningful Mode-A testing *and* it is what a prospect actually sees in a demo (same "realistic volumes matter when presenting" argument as the pagination item). **No conflict with [[ADR-143 — AI-Assisted Development Boundary]]:** content records are not personal data — it is *recipient* data that must be pseudonymized, not editorial content. Source: user, 2026-07-31 (raised as a blocker before the Mode A build).

- 🔴 **[Feature]** **Recall past AI suggestions after one has been applied — a manager-visible run history.** Surfaced 2026-08-02 (user, first live Claude run). Today the Mode-A suggestion flow is write-once from the manager's point of view: campaign → *Suggest subject & preheader* → pick one → the chosen text lands on the variant and **the other two options vanish**. Re-opening the variant shows only the applied subject line; the discarded alternatives are unreachable through the UI — even though `AIRunDB` already persisted the full model output, the prompt version that produced it, and the token cost. The data is there; only the surface is missing. **Two options considered; the user prefers (2).** *(1) Always allow re-selecting the other suggestions* — keep the option list visible on the variant after one is applied, so a manager can switch. Cheapest, but only ever covers the most recent run. *(2) A history view* — a separate page listing past runs with their prompt version and all suggestions, so a manager can look back later instead of reading the database by hand. Preferred: it covers *every* run rather than the last one, it is where "which prompt version produced this?" naturally belongs, and it serves the audit purpose the data is already being kept for. The two aren't exclusive — (1) is a subset of (2) — but (2) is the target. **Audit angle worth noting:** [[ADR-140 — AI Capability Layer]] §3 requires these runs to be recorded, and they are — but today the only way to *read* them is SQL, so the audit trail exists without being usable by the person it is meant to serve. Source: user, 2026-08-02 (post first real Claude generation).

- 🔴 **[Feature]** **Per-task / per-feature model selection — the direction [[ADR-144 — AI Data and Model Governance]] §2 already documented, now with concrete reasons to build it.** Surfaced 2026-08-02 (user). Today the model is one global setting (Settings → AI model) plus an `ANTHROPIC_MODEL` environment override, so every task calls the same model. ADR-144 §2 already records **per-task model choice as the documented direction**, with the POC deliberately shipping one model plus a "how to add and connect more models" guide — so this is that build, not a new decision. **Why it now has teeth:** tasks differ enormously in what they need. Subject-line generation from supplied content is not frontier reasoning — Haiku 4.5 runs it at roughly a fifth of Opus 5's price ($1/$5 vs $5/$25 per Mtok), which at fan-out scale is the difference between ~$1,800 and ~$9,100 per campaign (see the Mode-A × decision-slot Needs-ADR item). Content enrichment at ingest, outcome analysis, and copy authoring each sit at a different point on the cost/capability curve, and one global setting forces them all to the most expensive one. **Scope to design:** (a) selection **per AI feature**, not globally — the natural home is beside the prompt, which is already per-task and manager-owned (ADR-140 §4), making "prompt + model" one versioned unit; (b) **multi-vendor, not just multi-model** — the user expects deployments to mix providers (one vendor for creative copy, another for flows/agents), which the `AIProvider` adapter already permits but the single global setting forbids; (c) keep the **governed-list** posture — a per-task choice *within* what the deployment has enabled (ADR-140), never free text; (d) decide whether pricing metadata belongs with the model registry (`app/ai/pricing.py` already holds the rates, so per-task selection would let the spend readout attribute cost **per feature**, which is what makes the cheap-model argument checkable rather than theoretical). **Interaction with prompt versioning worth settling at the same time:** if the model becomes part of a task's configuration, changing it should arguably mint a new prompt version — the same prompt on a different model is a different thing, and an audit row resolving to "prompt v3" should resolve to the model it ran on too. `AIRunDB` already records the model per run, so the history exists; the question is whether the *configuration* should version together. Source: user, 2026-08-02.

- 🔴 **[Feature]** **Couple extended thinking to the output ceiling — enforce the rule instead of asserting it.** Surfaced 2026-08-02 (`/interview-review`, AI Q7). Extended thinking is off by default for a cost-correctness reason: `max_tokens` caps thinking *plus* reply, so a task declaring a 400-token ceiling could spend the whole budget reasoning and return a truncated answer (`claude.py:89-96`). The adapter comment states that a task enabling reasoning must raise its ceiling to match — *"the two must move together"* — but **nothing enforces it**: `thinking` is a constructor argument on the adapter, `max_output_tokens` is a constant in the task file, and no code relates them. The first task that flips thinking on and leaves its ceiling at 400 silently reintroduces the exact failure the default prevents. **Latent, not live** — nothing enables thinking today, which is why this is a guard to add rather than a bug to fix. **Agreed fix: a floor** — refuse, or warn loudly, when thinking is enabled and the declared ceiling is below a sane minimum. **Keep it simple — user's calibration for the whole token-control area (2026-08-02):** the warn/hard-stop pair already exists and today most companies simply notice they have run out; this does not need to be inventive, original or perfect and can adapt over time. Its only job is to buy a reasonable amount of time while automations are running, so someone gets notified, escalates and obtains more budget before the next big prompt lands. Do not gold-plate. Source: [[Interview Prep - AI]] → AI Layer Q7.

- 🔴 **[Feature] — direction + documentation, not a POC build.** **Read the remaining AI budget from the company's AI source instead of a local setting.** Surfaced 2026-08-02 (`/interview-review`, AI Q6). Today the cap is two numbers an admin types into Settings, and prices live in a hand-maintained `MODEL_PRICING` table — fine for the POC, and the manual path should stay as the default. **The structural problem it hides:** a company's AI budget is *company-wide*, and this platform will not be the only system in the company consuming tokens. A locally-configured cap therefore governs one consumer of a shared pool, and will drift from reality the moment a second system draws on it. **Direction:** allow the remaining budget (and ideally current prices) to be **fetched from the company's AI/token source** — an API the deployment points at — with the local setting as the fallback. Two things fall out for free: the platform stops being the authority on prices, so the **stale-price risk disappears** rather than needing a freshness mechanism; and the pre-call gate keeps working unchanged, since it only needs a "remaining" number, not where it came from. **Deliverable is a how-to, not an integration** — same posture as the swap-send-provider guide: describe the seam and one worked example, do not ship a connector. Pairs with the per-feature model selection and count-tokens escape-hatch items; write the three together. Source: [[Interview Prep - AI]] → AI Layer Q6.

- 🔴 **[Feature]** **A system-mail channel on its own domain — and probably its own transport.** Surfaced 2026-08-02 (user), during the security-base build. **Sign-in codes are the first system email, and they will not be the last:** approval notifications, AI-suggestion alerts and any other operator-facing message belong on the same channel. This is a **third** outbound category the architecture had not named — marketing customer / transactional customer / **system internal** — and it is not a flavour of transactional, because it is not customer-facing at all: no consent question, no unsubscribe semantics, almost no volume. See sub-point (b) of the transactional Needs-ADR item for the reputation reasoning. **Already in code:** `SYSTEM_MAIL_PROVIDER` (defaults to `mock`) and `SYSTEM_MAIL_FROM` in `app/auth/service.py`, with a startup warning when the sender falls back to the marketing one. Those helpers live in the auth module only because auth is currently the sole caller — **move them to a shared helper as soon as a second consumer appears**, or the second one will quietly reimplement them. **Still to do: (1)** verify a separate domain or subdomain for system mail and set `SYSTEM_MAIL_FROM`; **(2)** decide whether system mail should use a **different transport entirely**, not merely a different domain. The user's suggestion — the hosting provider's own SMTP, e.g. Strato — is a good fit and worth evaluating: it makes the channel genuinely independent of the ESP, so an ESP outage, suspension or quota cannot lock operators out of the platform, which a separate domain on the *same* provider does not achieve. Volume fits (a handful a day against shared-hosting limits of a few hundred), it is already paid for in the hosting package, and reputation is separate by construction. **Costs to weigh:** SMTP is a different transport from the HTTP adapters, so it needs a `DeliveryProvider` implementation (small — `smtplib` is stdlib); there is **no feedback loop** (no webhooks, no bounce events), which is fine for system mail but means a silently failing address goes unnoticed; and shared-hosting IP deliverability is variable enough to test rather than assume. Credentials follow [[ADR-152 — Secret and Credential Handling]] — environment, never the database. **Bonus worth noting for the playbook:** an SMTP adapter would be a *third* worked example of the provider contract, and arguably a stronger no-vendor-lock-in demonstration than a second SaaS ESP, because SMTP is the universal fallback every company already has and proves the contract is not API-shaped. Source: user, 2026-08-02 (security base build).

- 🔴 **[Feature]** **Documented escape hatch for a model that cannot count tokens — "what to do if your AI provider has no counting endpoint".** Surfaced 2026-08-02 (`/interview-review`, AI Q2). `count_input_tokens()` is a **required** abstract method on `AIProvider`, deliberately: ADR-144's spend cap is a pre-call gate, and an adapter that cannot report a worst case cannot be gated, so making it optional would let some models silently bypass the cap (ADR-101, capabilities are explicit). The requirement stays. **But a company whose chosen model has no counting endpoint currently has no path at all** — the contract simply refuses the adapter, which is the wrong failure for a reference architecture whose whole pitch is "swap the vendor." Needs: a documented way to add such an adapter, an explicit statement of **what is lost** (the pre-call gate — the cap degrades to post-hoc, or the company sets a hard run-count limit instead), and ideally a structural seam so opting out is a visible, deliberate configuration rather than a fork of the contract. Judged unlikely to bite — a model sold into the EU that cannot tell you what a call cost is hard to imagine — but the cost of being wrong is an adopter who cannot use their own provider. Fits alongside the per-feature model selection item and the still-unbuilt EU-hosted adapter that ADR-144 §1 committed to; write it with those. Source: [[Interview Prep - AI]] → AI Layer Q2.

- 🔴 **[Feature]** **Inbound machine authentication — issuable API credentials for external systems (orchestrator, CRM, DWH, CDP, website forms).** Surfaced 2026-07-31 (user). **Not optional and not "later" — it is a prerequisite for Mode B.** [[ADR-142 — Autonomous Workflows and the Automation Boundary]] decided the platform exposes **triggerable-action APIs** that an orchestrator calls, and that external systems may write and explicitly override the suppression gate (the "website form fires *this recipient must get this*" case). Every one of those calls has to be authenticated, so Mode B is not actually usable until this exists. The Cluster-3 ownership finding sharpens it: **automation is usually a different department**, so credentials must be **issuable and revocable per integration**, never one shared secret. **Scope to design:** (a) credential issuance / rotation / revocation for machine callers; (b) **per-integration authorization** — which system may invoke which actions (n8n may trigger a send; a website form may only pin a recipient); (c) audit — machine-initiated actions land in the same action history ADR-142 already requires. **Distinct from the parked Security chapter**, which covers *human* auth (login/SSO/roles) — this is *machine* auth: related, separately scoped. **Hypothetical driving scenario — explicitly NOT a confirmed requirement (real client, presented to 2026-07):** the client has **not signed the CDP contract**, so nothing is implemented. Their current *assumption* is that the CDP will be the running AI system, offering only prompting — a user types *"collect everyone interested in X from the last two weeks and in N days send them something interesting"* — with the CDP perhaps assembling an audience while **another system translates intent into action**. **The user intends to challenge that assumption:** if the CDP's AI doesn't actually deliver results, there is little reason to use it, and this platform — or its connection to something like n8n — may be the better workflow. **So this particular integration may never be needed**; it is recorded as *one hypothesis about who calls the API*, not as a committed requirement. **What is not hypothetical is the underlying need:** inbound machine auth is required for Mode B regardless of which system turns out to be the caller. The scenario stays architecturally instructive — it shows ADR-142's boundary holding with an **LLM-speaking orchestrator** in n8n's role — and adds one design consideration: the action API should be **describable as tools** (name + description + input schema) so an LLM-driven caller can consume it without bespoke glue; MCP is the emerging standard for exactly this. **Direction only, not a build decision** (per the "don't over-commit to unvalidated detail" principle). Source: user, 2026-07-31.

- 🔴 **[Feature]** **Dev-data pseudonymization guard — a Mode-C safety property, not only a privacy one.** Decided 2026-07-31 (AI-layer interview, Cluster 4 / Q20b). **Problem:** the standard industry habit is copying production data into a "dev" environment — the user reports every company he has worked in or for ran exactly that *pseudo*-dev setup, which forces permanent caution inside the environment that exists so people *don't* have to be cautious. Under Mode C (AI-assisted development — **including marketers vibecoding**, not just developers) that habit also silently violates [[ADR-144 — AI Data and Model Governance]], since an assistant reading the dev DB is reading real recipient PII. **Design:** (1) **Deterministic pseudonymization, not hashing** — stable fake-but-realistic values (same input → same output) so joins, dedup and per-recipient logic still work; a hash would protect the data and simultaneously destroy the reason to have a dev environment. (2) **Schema-declared PII fields, not content sniffing** — the models already know which fields are personal, and ADR-144's per-task PII filter needs the same metadata, so **one declaration serves two consumers**; free-text/JSON sniffing is a documented best-effort *extension*, not v1. (3) **Exempt-domain allowlist** (e.g. `PII_EXEMPT_DOMAINS`) — addresses at the company's own domains stay real so provider testing and marketer campaign tests still work; **must accept multiple domains** (different brands, external agencies). Chosen over a third `dev → testable → prod` environment, which costs extra infrastructure and merely *relocates* the risk; the allowlist caps AI blast radius at **your own employees instead of your customers**. (4) **Non-routable addresses for everyone else** — this also closes the gap that environment separation *cannot* contain outbound email (Q19): with no deliverable customer addresses in DEV, a stray real send reaches nobody. (5) **Loud DEV startup assertion** that fails on unpseudonymized data **and reports what it exempted** — a widened allowlist must be visible, never silent; no wildcards. **Change-effort requirement:** declaration lives on the models (written once, untouched at deploy time), **policy is environment configuration**, so dev→prod is a config difference rather than a file edit (the user's Condor experience: moving many files between environments reliably produces typos and omissions). Composes with the existing layers: mock provider as DEV default → recipient cap → exempt-domain allowlist → assertion. Cross-references the parked **Security chapter** (key storage, GDPR/ISO, SSO, roles). Source: user, 2026-07-31 (AI-layer interview, Cluster 4).

- 🔴 **[Feature]** **Simple A/B test component + random audience split — POC scope.** Decided 2026-07-31 (AI-layer interview, Cluster 3 Q17). Every marketer will ask for A/B testing, even though the architecture's own thesis is that personalization makes *content-level* A/B largely redundant over time (**rebranding stays a genuine exception**) — so ship the simple version and let the AI/strategy workflows earn the case for retiring it. **POC scope:** (a) a **random split** function in the segment builder (definitely build); (b) a small A/B component that selects between **variants or subject lines** with a **percentage split**, so one send divides into *x* parts; (c) extend the Mode-A subject suggestion ([[ADR-141 — In-App Assistive AI Actions]]) so that alongside **"use suggestion"** there is **"test suggestions in A/B setup"** — Mode A removes the friction of *writing* a second subject line, this removes the friction of *testing* it (two different problems; conflating them was an error caught in the Q17 discussion). **Sticky assignment for cycle-length tests:** if a test runs across a cycle, a recipient must *stay* in their group — a stateless random split would re-randomize every run. **No new entity needed — reuse the existing pin mechanism** (`resolve_audience`'s `… ∪ pins`): randomize once, materialize the split as pinned groups, subsequent runs read the pins. **Out of POC — library documentation only:** multivariate testing, more complex test designs, automated winner rollout. **Watch item:** **preheader may become irrelevant** as mail providers replace it with AI-generated summaries — worth confirming before investing in preheader-specific testing. Source: user, 2026-07-31 (AI-layer interview, Cluster 3 Q17).

- 🔴 **[Feature]** Reevaluate the decay model: **calendar-time vs. activity-relative decay** — surfaced 2026-07-15. Today decay is measured in absolute calendar time (`age = now - occurred_at`). Edge case: a recipient on holiday for 90 days returns with (arguably) unchanged interest, yet their signals have decayed as if they'd disengaged. Open question whether to slow/pause decay during inactivity (measure decay in "email opportunities seen" or active time rather than wall-clock). **Leaning: probably leave it as calendar-time** — a genuinely interested person reads newsletters even on holiday, so continued non-engagement *is* signal, and decaying + starting fresher on return may be the right call. Noted for reevaluation with real data, not a change now. Depends on / relates to [[ADR-132 ...]]. Source: user, 2026-07-15 (signal-layer design session). **Update (user, 2026-07-15): will most likely stay calendar-time / not build this.** Reasoning: if someone didn't read for 3 months, they also *lived* 3 different months — we can't assume their interests are unchanged from before, so re-earning the signal is more honest than pausing decay. Don't add complexity for a case we can't actually verify. If a specific company disagrees and wants activity-relative decay, the decay function is a code/plugin swap (per ADR-132's "different decay model = code change") — a good candidate for an open-source-community contribution rather than core. Likely to be moved to **Won't Do (core)** unless a real adopter pushes for it.

- 🔴 **[Feature]** Anti-bubble / exploration in the decision layer — "even when the engine is confident about a recipient's category, every once in a while show a *different* category to avoid the filter-bubble trap." An explore-vs-exploit behavior in the decision strategies (fed by signals), NOT signal storage — surfaced 2026-07-15 during the [[ADR-132 ...]] signal design. A recipient who only ever gets their top category gets stuck; occasional diversity keeps the profile honest and gives new interests a chance to surface. Needs a small design (how often, how the alternative category is picked — random vs. second-ranked vs. least-recently-shown). Depends on the signal layer landing first. Source: user, 2026-07-15 (signal-layer design session). **Update 2026-07-31 (AI-layer interview, Cluster 3 / Q17): this now has a concrete first use case and a named objective.** For **cold-start recipients** (a brand-new subscriber with no signal), the Mode-A suggestion button on **welcome cycles/emails** should surface *"here's what brings the **most diverse engagement** across other recipients"* — i.e. pick for **information gain (data/engagement), explicitly not conversion**. That is exactly this explore-vs-exploit behavior, arriving via the cold-start door rather than the filter-bubble door. Pairs with the DOI/subscription-context seeding item below (which supplies the *first* Anhaltspunkt so exploration starts from something rather than nothing).

Document the extension point + one worked example when a real adopter needs it. Source: user, 2026-07-15 (signal-layer design session).

- 🔴 **[Feature] — Brand/theming structure across stages (note options now, implement in final MVP package).** Surfaced 2026-07-26. Goal: let each adopting company drop in their own styles so the whole architecture looks consistently *theirs*, across the (at least) two rendering stages — **web** (the Jinja management UI) and **email** (rendered newsletters). **Current state:** email is already the "drop a file" pattern — `storage/email_modules/brand.css` (~79 lines) is auto-inlined by the renderer and uses class names matching the module templates (`.module-headline`/`.module-button`/`.module-hero`…), with a header comment "replace per project". **Web has no brandable file** — it's raw Bootstrap 5 via CDN in `base.html`. There is **no shared source of truth** between the two, and **no preprocessor/build**. **Design answer to the questions raised:** (1) *One file for both stages is possible but a bad idea* — web and email have fundamentally different CSS capabilities (email = inlined, table-based, limited client support; web = full modern CSS), so a single stylesheet can't serve both cleanly. (2) *"Is there a CSS 'MJML'?"* — yes, the analogues are **CSS preprocessors** (Sass/SCSS, Less: variables, nesting, mixins, partials — write maintainable source, compile to targets) and **design tokens** (brand primitives — colors/fonts/spacing/radius — as the single source of truth, e.g. CSS custom properties, or a Style-Dictionary-style build that emits per-target files). Neither is "20,000 lines" — the point is a *small* token file + component partials. (3) **Recommended structure:** split **tokens** (what the brand *is* — a tiny file the company edits) from **stylesheets** (how tokens are applied per stage). One token source → two outputs: web consumes tokens via CSS custom properties (native support); email keeps a `brand.css` but its values come from the *same* tokens, **baked in as concrete values at build** (email clients don't support CSS variables reliably, so they must be inlined — which the renderer already does via `css_inline`). (4) *Separate files + a frontend to manage?* — a full in-app CSS editor is a footgun; better is a light **brand-tokens panel** (pick primary color / font / logo — manager-friendly, writes tokens, akin to the existing settings layer) while raw stylesheets stay files for developers. (5) **Consistency / no redundant classes** — the email side already enforces a shared `.module-*` class convention; extend the same discipline: one token source, a documented component-class vocabulary shared by both stages, component-scoped (not page-scoped) classes. **DECIDED direction (2026-07-26) — simpler than the tokens→two-outputs idea above; handle the two stages *differently*, no shared token pipeline:**
- **Email** keeps `brand.css` as a **separate, full-flexibility plain-CSS file** (developer/designer-owned, drives preview + MJML). Email is the stage managers actually care about visually — "I want rounded buttons, a shadow behind the box", etc. — so it gets **full raw-CSS control**, not a constrained token set. No abstraction forced on it.
- **Web** (management UI) gets a **small, simple brand-palette frontend** — **colors, fonts, sizes, logos only** (settings-layer style, applied to the UI via CSS custom properties). Deliberately *not* full CSS; keep it simple.
- Net: email = file + full flexibility; web = simple palette UI. No build step, no preprocessor. Consistency still comes from the shared `.module-*` class vocabulary on the email side and a small fixed token set on the web side.

**Scope (per working style):** lands in the final MVP package; the web palette is small and self-contained enough to build standalone earlier if wanted. Source: user, 2026-07-26.

- 📋 **System email: transport, templating, triggering — and which provider may be selected where.** Surfaced 2026-08-02 (user), during the security-base build. Sign-in codes made system mail real, and four questions came with it that the architecture has no answer for. **(1) Should a separate transport be *forced*?** The user asked whether companies must use SMTP for system mail, may freely point it at the marketing sender, or are forced with code as the escape hatch. **Suggested fourth option: allow it, default safely, warn loudly** — `SYSTEM_MAIL_PROVIDER`/`SYSTEM_MAIL_FROM` already exist, the default is mock, and startup warns when system mail falls back to the marketing sender. Same idiom as ADR-152's write-only credentials and ADR-144's PII default: safe by construction, deliberate opt-out, never silent. Forcing contradicts the "adapt it to your setup" posture, and some deployments genuinely cannot use SMTP (cloud providers commonly block outbound port 25). **(2) Do self-hosting companies have an SMTP option?** Yes, and the worry dissolves once you notice **SMTP is a transport, not a hosting model**: a self-hosted Postfix/Exim, a Microsoft 365 or Google Workspace relay (the most likely real answer for a Mittelstand company, which already has one), or a transactional service's SMTP endpoint all speak it. One adapter serves self-hosted, cloud and SaaS-relay identically — which is exactly what makes it a good universal fallback. Caveat to document: ports 587/465 rather than 25, and SPF/DKIM/DMARC on the system subdomain. **(3) Should an SMTP/Strato provider appear in the campaign "send from" menu?** Resolved in principle — **the API-vs-SMTP framing and the gating rule are now recorded in [[ADR-101 — Provider Capabilities Are Explicit]] (addendum, 2026-08-02)**. Short version: capabilities describe the configured *provider instance*, not the protocol, because an ESP's SMTP relay still fires webhooks while generic host SMTP does not; combined with [[ADR-106 — Bounce and Complaint Feedback Is Mandatory]], a provider that cannot report bounces may not be selected for a marketing send. **What remains is the build:** capabilities are documented per adapter but not declared in a form the send path can read, and the provider selector still offers every registered name. That enforcement point is the actual work here. **(4) How are system emails built, and who triggers them?** Not from the content catalogue: [[ADR-012 — Content Records Represent Communication Units]] describes editorial content, and a login code is not one. Suggested: **dev-owned Jinja templates in the repo**, with a small set of substitutable values (product name, sender, locale) rather than a WYSIWYG — the inverse of ADR-140 §4's reasoning, since a manager should not be able to edit the email that lets people in. On triggering, [[ADR-142 — Autonomous Workflows and the Automation Boundary]] already gives the spine: **the platform owns the action, the orchestrator owns the flow** — so "send an approval notification" is a platform action and n8n decides *when*, rather than n8n composing and sending the mail itself. Otherwise every orchestrator reimplements the templates and sender config, and [[ADR-153 — Audit and Accountability]] loses the record. **Note how much of this is already implied** by ADR-101/106/012/142 — the ADR may be mostly a matter of stating the derivations and deciding (1). - 📋 **Concurrent actors: a contention model, not just row locks.** **Promoted and broadened 2026-08-02** (`/interview-review`, AI Q4) from the earlier Features item "systemic pattern for concurrency guards", which was scoped to database write races and is superseded by this. The user's framing: *"this should be a general architectural discussion — we will need a systemic concept for this."* **Three distinct sub-problems, and only the first is a locking question.** **(a) Human ↔ human.** Two managers editing the same campaign at the same time. Needs presence ("person A is working in this campaign"), an **unlock** path for when they leave the tab open and go home, and edit-conflict detection — none of which exists anywhere in the project today. **(b) Human ↔ AI — a precedence *policy*, not a mechanism.** The rule the user wants: **if a real person is working on something, AI stands back.** This cannot be derived from database semantics; it is a governance decision about who yields, and it belongs beside [[ADR-140 — AI Capability Layer]]'s "a human can always interfere" posture. **(c) A queue with a log.** Whether write actions route through a queue that records *what was attempted*, so that an action which never fired, or fired and failed, still leaves "when and why" behind. This connects directly to [[ADR-142 — Autonomous Workflows and the Automation Boundary]] (machine actions land in the same action history) and to [[ADR-153 — Audit and Accountability]] (which is the natural home for "attempted but did not run"). **Concrete instances found so far, all symptoms of the same missing concept:** the Overrides Q4 outcome-delta race (`record_outcome_delta`, read-modify-write with no lock); the Delivery Q5 double-send race; and now the **AI spend-cap TOCTOU** — `tokens_used()` reads the ledger, the gate compares, `_record()` writes, with no reservation in between, so two concurrent runs can both pass a gate that only one should (`service.py:193`). Note `send_send_instance` already uses `with_for_update()`, so the project has *one* ad-hoc answer and no convention — which is exactly the problem. **Why it is more urgent than it looked:** AI runs are the most likely thing to actually go concurrent first (Mode B fan-out, or the per-rendering generation option), and the AI instance is the one where losing the race costs *money* rather than consistency. Blast radius there is small and bounded — roughly one racing run's worst case, about a cent — so this is not an emergency, but it is the third instance and the pattern is what needs deciding, not the instance. **Sequencing note:** intersects the Security base (sessions, actors, audit) about to be built — presence and "who holds this" need an authenticated actor to attach to, so there may be real efficiency in designing this alongside rather than after. - 📋 **Mode-A subject/preheader generation vs. decision-slot content — today's button only works for manually composed campaigns.** Surfaced 2026-08-02 (user, immediately after the first real Claude generation). **The problem.** [[ADR-141 — In-App Assistive AI Actions]]'s "suggest subject & preheader" reads the variant's module content and returns **3 options for a human to choose from**. As soon as the campaign uses **decision slots** ([[ADR-083 — Personalization Happens Inside Variants Through Decision Slots]], including AI-driven selection) two things break. **(a) Timing** — the content does not exist until resolution has run, so the prompt has nothing real to read; the task can only run *after* resolution. **(b) Cardinality** — personalized resolution produces *many* renderings, each needing its **own** subject/preheader, so the task must emit **one pair per rendering** rather than three options for a human to choose between. Three suggestions × N renderings is not reviewable by a person, so the "human picks one" approval step that makes Mode A safe does not survive the jump — which puts this squarely against [[ADR-082 — AI May Recommend but Not Publish]] and needs an explicit decision rather than an implicit drift. **Options the user floated (recorded as options, not decisions).** *(A) A second, separately selectable action*, offered only once a campaign contains ≥1 decision slot. Because it is per-rendering it needs a **cost warning before it runs** — "run the decision engine now + prompt every rendering will cost ×N tokens", where N is the rendering count — and a **second warning if the manager later re-runs the decision engine**, since previously generated subject/preheader pairs may no longer match the content they were written for. *(B) Offer it only at schedule/trigger time* — the only moment at which "this **is** the content" is guaranteed. The manager accepts up front that the email ships AI-written subject lines unreviewed, softened by a "show results" view and a "cancel send" escape hatch. *(C) Leave the campaign-level button exactly as it is* — the 3-suggestion human-picks-one flow — but **scope its input to manually selected content only**, or at minimum to the campaign's selected categories, so it never silently produces a subject line for content that will be swapped out per recipient. (A/B/C are not mutually exclusive: C describes what the existing button should be narrowed to, whichever of A or B is added alongside it.) **Interactions to settle with it:** the per-rendering cost multiplier interacts with the spend cap ([[ADR-144 — AI Data and Model Governance]] §5) — a pre-call gate that today prices *one* call must price N; the "re-running decisions invalidates generated copy" problem is a dependency/staleness question the snapshot model may already have a place for; and the whole thing sits on top of the unresolved **resolution ordering + scope** item directly below, since "how many renderings are there" is exactly what that item hasn't decided yet. **Not written as an ADR deliberately** — the user's standing rule is that ADRs record *his* decisions, reached one question at a time through the interview process, so this is captured here as faithfully as possible and left for that conversation. Source: user, 2026-08-02 (post first real Claude generation).

  **Update 2026-08-02 — cost modelling, and a finding that reframes the question.** *(Same session; still not a decision — the user's read is that this "needs more thinking".)* **(1) The cost.** Distinct renderings are driven by slot combinatorics capped by audience size, **not** by recipient count. With 2000 content records across 40 categories (~50 candidates per category once a slot filters by category), distinct renderings ≈ `min(recipients, 50 ^ slots)`. At 1M recipients: 1 slot → 50 renderings (~$0.46); 2 → 2,500 (~$23); 3 → 125,000 (~$1,140); 4+ → capped at 1M (**~$9,100–12,000 for a single campaign**). Basis: the measured live run, ~700 in / 225 out on Opus 5 at $5/$25 per Mtok = $0.0091/call. **Two consequences for any warning UI:** it must count **distinct renderings, not recipients** (or it overstates by ~8× in the 3-slot case), and **dedupe-by-combination belongs in the design rather than as a later optimisation** — identical renderings take identical subject lines, and that alone is worth ~8× here. Cheaper model (~5×) and prompt caching (~12%) are the next two levers; note caching only starts paying at fan-out scale, unlike the single-campaign case where it was correctly skipped. **(2) The stronger finding is that cost is the *weaker* objection.** "Which of these 50 governed candidates suits a recipient scoring hiking 0.82 / wildlife 0.61" is a ranking problem over a vector that has already been computed — not a language problem. `recipient_top_score` answers it deterministically in microseconds, auditably, and A/B-testably; an LLM answering the same question costs ~1¢, is non-deterministic, resists clean A/B measurement, adds latency, and can hallucinate a content id. **At zero cost it would still be the weaker mechanism.** Industry shape appears to agree (public positioning, not verified internals): the large suites — Salesforce Einstein Content Selection, Adobe's equivalents — *do* select content per recipient at scale, using ranking/propensity models trained offline and scored at negligible marginal cost, and place *generative* AI at authoring with a human in the loop. That is the same split this architecture reached independently: **discriminative ML in the per-recipient path, generative AI at the edges.** So "they only build an email, not a personalized one" is not the explanation — they personalize per recipient, they just don't route it through a language model. **(3) Where the LLM does earn its place** — all off the per-recipient path: content **enrichment at ingest** (categories, tone, angle, summary — once per record, ~$10 for the whole 2000-record catalogue, and it improves every subsequent decision permanently — the highest-leverage item on this list); **authoring** (Mode A, human picks); **periodic outcome analysis** proposing strategy/weight changes (Mode B); and **explaining one decision** on demand (ADR-085). **(4) The user's own reframe:** move this out of campaign level and into the Mode-B analytic flow — *"check decisions + history and suggest updates to the algorithms"* — so **the AI touches the rules and the rules touch the recipients**. Costs a few dollars a month instead of thousands per campaign, and fits what is already decided ([[ADR-082 — AI May Recommend but Not Publish]], [[ADR-142 — Autonomous Workflows and the Automation Boundary]]'s orchestrator boundary) without amending either. **Refinement:** what should be ruled out is anything whose cost **scales with audience size** — a *campaign-scoped* analysis call ("this underperformed with segment X, what would you change?") is one call and cheap, so a blanket "no AI at campaign level" would be too broad. **(5) Sub-question that may deserve an ADR of its own: "AI" currently means two different things in this architecture.** [[ADR-080 — Human-governed Taxonomy Before AI Selection]] / [[ADR-081 — AI Ranks Within Governed Candidate Sets]] / ADR-082 are written model-agnostically — **ADR-081's "AI *ranks* within governed candidate sets" is fully satisfied by a gradient-boosted ranker and does not imply a language model** — while ADR-140–144 describe an LLM capability layer. Nothing currently states which kind belongs where, and that ambiguity is precisely what allowed an LLM to be costed into the per-recipient path in the first place. Stating it (*selection is learned ranking; generation is language*) would prevent the drift structurally instead of by remembering. **(6) Working conclusion to test, explicitly not yet decided:** the per-rendering generation option may not be "parked pending budget" but "shouldn't be built" — the comparison a buyer actually runs is not AI-personalization vs none, it is **LLM-per-recipient vs ranking-model-per-recipient**, and the latter wins on cost, latency, determinism *and* auditability simultaneously. That is a design without a case rather than a price to negotiate. Needs the interview before any of it goes into an ADR. Source: user + cost modelling, 2026-08-02.

- 📋 **Dynamic decision content × audience: resolution ordering + scope (build slot → suggest audience → run resolution?).** Surfaced 2026-07-26. When a campaign's content is *dynamic* (decision slots resolving per recipient, ADR-083), the plan-a-send flow has an unresolved ordering/scope question that the current build papers over. **(A) The circular dependency.** "Suggest audience" derives the audience *from* the campaign's content categories — `campaign_category_scores` (`audience/service.py`) reads module content records **plus already-resolved decision picks** (`DecisionResolutionDB.content_record_id`). But decision-slot content is chosen *per recipient*, so the content's categories depend on *who is in the audience* — which is the thing we're trying to suggest. Chicken-and-egg. Today it's masked: suggest-audience just reads whatever resolutions already exist (seeded/prior); for a fresh campaign whose content is *only* decision slots with no resolutions yet, it sees only the direct module content and ignores the slot's candidate pool entirely. **Candidate fix to break the loop:** suggest the audience from the slots' **candidate-pool** categories (the `candidate_filter.category_ids` + the categories of candidate content) rather than from already-resolved picks — i.e. target people interested in what the campaign *could* show, then resolve per person *within* that audience. **(B) Resolution scope — on segment / on every person / both?** Two scopes exist *implicitly* today via a strategy's `requires_recipient` meta (`decision/service.py`): personalized strategies (e.g. `recipient_top_score`) resolve **per recipient** (one row per (slot, recipient), new row only when the pick changes); non-personalized (e.g. `top_score`) resolve **once per slot** (recipient_id=NULL, single row updated in place). What does **not** exist is a first-class **per-segment** scope — "audience group A gets pick X, group B gets pick Y" as one resolution per segment rather than per individual. Options to decide: (i) per-person only (max personalization, but O(recipients) resolutions + the snapshot/storage cost already flagged in the rendered-HTML Needs-ADR item); (ii) per-segment (one resolution per audience group — far cheaper, coarser, loses individual personalization); (iii) both, selectable per slot (most flexible, most surface area). Interacts with the "freeze vs re-run at send" audience mode already built (`488c837`) and with batching (per-person resolution favors small batches; per-segment favors one blast). **(C) The meta-question the user is really asking: guide vs. implement.** Do we (1) document this as a **playbook guide** — "these are the steps: build slot → resolve → suggest audience → send, and here are the scope trade-offs" — leaving adopters to wire their own order/scope (max flexibility, fits the reference-architecture + playbook ethos, less turnkey); or (2) **implement** an opinionated codified flow in the product (a wizard-like build-audience → resolve → send path) that accepts **less flexibility** for a working out-of-the-box experience? Likely answer is a mix (a documented recommended flow + a sensible default implementation with escape hatches), but it needs deciding as an ADR before more of the plan-send/suggest-audience surface hardens around an unstated assumption. Ties to: ADR-083 (per-recipient decision personalization), the rendered-HTML/snapshot storage Needs-ADR item (per-person resolution multiplies stored artifacts), the batching/send-timing Needs-ADR item, and the freeze/re-run audience mode. Source: user, 2026-07-26 (Phase 3 audience/send session).

- 📋 **Transactional sends — consent model, sending reputation, and whether they reuse the email modules.** Surfaced 2026-07-31 (user). The architecture today only does *marketing* communication: every send passes the consent floor (`CONSENTING_STATUS = "opted_in"`), and content comes from the governed catalogue. Transactional mail (order confirmations, password resets, booking details, masterclass signups) breaks all three assumptions at once, and **this may be a dealbreaker rather than a nice-to-have** — "why adopt a new system if it only handles marketing?" Three linked questions, none decided:

  **(a) Consent.** Transactional mail goes to people *without* marketing opt-in, by design. Does the model need **two distinct permissions** (marketing consent vs. a transactional/legitimate-interest basis) rather than the single `consent_status` gate in [[ADR-122 — Minimal Consent Model Required]]? Note the hazard already recorded in `docs/playbook-strategy.md` (Decision Log 2026-07-11, item 4): **some providers, e.g. Selligent, ignore opt-outs entirely on API-triggered sends because they classify them as transactional** — so "the provider will sort it out" is exactly the assumption this architecture exists to avoid. Also to settle: hard bounce / spam-complaint suppression almost certainly must still apply to transactional (a dead address is dead either way), while a *marketing* opt-out must not block a password reset — meaning the suppression gate and the consent gate are not the same gate. Interacts with the suppression/opt-out data-model item below.

  **(b) Sending reputation — and it is a THREE-way split, not two.** *Corrected 2026-08-02 (user), after sign-in codes made the third category concrete.* Marketing and transactional should not share reputation: complaint rates on marketing degrade delivery of mail people actually need. But **system-internal** mail — to the company's own operators, not to customers — is a third category again, and must not ride on transactional either. Its failure mode is unique and circular: if transactional delivery degrades a customer misses a receipt, but if system delivery degrades **nobody can sign in, including the person who would fix whatever caused it**. Transactional volume and complaint exposure are still customer-driven and outside the company's control, so sharing with it reintroduces the risk. So: **marketing customer / transactional customer / system internal**, three senders. Options per stream: a **separate provider**, or at minimum a **separate verified domain or subdomain**. The provider layer is already an adapter ([[ADR-100 — Provider Layer as Send and Feedback Adapter]]) and from-address is selectable per send, so the seam exists; what is undecided is whether "which stream a send belongs to" becomes a first-class concept rather than a manual from-address choice. See the system-mail channel Feature for the third stream, which now has running code.

  **(c) Do transactional emails reuse the existing modules, or get their own?** The real fork, because it decides how variables work:
  - **Reuse the marketing modules** — **PRO:** far less work, one module library, one rendering path. **CON:** needs a **global variable solution that is not limited to catalogue fields** — a transactional payload arrives as arbitrary JSON from an external system (order number, seat row, reset link), so rendering must interpret JSON directly rather than resolve content records. That is a genuine extension of the merge-context concept in [[ADR-005 — Separate Snapshot State from Recipient Delivery Artifact]], not a small addition.
  - **Dedicated transactional modules** — **PRO:** variables become straightforward, since a module is written against a known payload shape. **CON:** you need **a module per email type** (each has different fields), and you **cannot combine JSON payload + catalogue content** in one email — which matters if you want the decision engine to add recommendations for a recipient who *does* have marketing opt-in.

  **Open sub-question:** should a transactional email to an **opted-in** recipient be allowed to carry decision-engine recommendations? Tempting (high open rates), but it mixes streams and risks the reputation separation in (b). Plausible answer is **"we deliberately don't do this"** — while noting an adopting company may want it anyway, so the honest question is whether they can **integrate it themselves at a documented seam** rather than whether we ship it.

- 📋 **Recipient suppression + opt-out reason model — "why is this person not getting communication?" as one auditable concept.** Surfaced 2026-07-31 (AI-layer interview, Cluster 3 / Q16). - 📋 **General data lifecycle / deletion & retention policy — not designed at all yet.** Confirmed during the interview review: the project has no deletion/cleanup story anywhere. Two concrete instances found so far, both symptoms of the same missing policy:
  - **Category/content record deletion vs. archival.** Categories accumulate historical value via preference/engagement scoring (`ContentCategoryAssignmentDB.score`, `RecipientPreferenceDB`) — hard-deleting a category breaks the ability to interpret that historical data (what a past engagement signal even meant). Leaning toward: never hard-delete a category/content record that has any historical usage — **archive** instead. An archived category stops contributing to *new* preference scoring; existing preference influence from it decays naturally over time (same mechanism as the not-yet-built Phase 3C signal decay, [[ADR-112 — Signals Use Time-Based Decay]]) rather than being force-zeroed. Only once a category is fully unused *and* decayed out would actual deletion become safe to consider.
  - **Snapshot lifecycle.** No uniqueness/idempotency key on snapshot creation means unbounded accumulation of near-duplicate snapshots per variant/recipient — consistent with "immutable append-only history" (ADR-061) but with no TTL, retention rule, or delete endpoint at all.

  Needs a dedicated ADR (none exists today) covering deletion/retention policy generally — likely also relevant to other accumulating tables (engagement events, decision resolutions, preference logs) once they're examined the same way. Tightly coupled to the Phase 3C signal layer design already flagged as open in `docs/playbook-strategy.md` §7. Source: [[Interview Prep - Content, Campaigns, Audience]] → Content Q6 (addendum); [[Interview Prep - Snapshots, Rendering, Email Modules]] → Snapshots Q6.

- ✅ **[Bug]** `create_decision_resolution` (`campaigns/service.py:235-257`) accepts arbitrary `content_record_id`/`content_version_id`/`recipient_id` with no existence validation before insert — depending on whether the DB engine enforces FK constraints (often off by default in SQLite), a bad ID silently creates an orphaned resolution row that only breaks later, at rendering's join-based lookup. Fix: no orphan row should ever be silently accepted — validate referenced IDs exist before insert (or ensure FK enforcement is actually on, e.g. `PRAGMA foreign_keys=ON` for SQLite) and return a clear error otherwise. Worth checking whether other `create_*` functions across the codebase have the same silent-orphan gap once this is fixed, since it's likely a systemic pattern, not unique to this one function. Source: [[Interview Prep - Content, Campaigns, Audience]] → Campaigns Q5. **Done 2026-07-12** — validates `decision_slot_id`, `content_record_id`, and (if given) `content_version_id`/`recipient_id` all exist before insert, applied at the function level so it protects both the direct API endpoint and the internal decision-execution path. Verified live: bad `content_record_id` rejected with a clear message; the internal execute-decision-slot path still works unaffected.

- ✅ **[Bug]** `add_member`/`bulk_add_members` (`audience/service.py:54-69,72-85,125-134`) do a SELECT-then-INSERT with no unique constraint on `(group_id, recipient_id)` — a TOCTOU race under concurrent calls can produce duplicate membership rows. Fix: add a DB-level unique constraint on `(group_id, recipient_id)` on `AudienceGroupMemberDB`, making it safe-by-construction instead of relying on the application-level existence check. Source: [[Interview Prep - Content, Campaigns, Audience]] → Audience Q3. **Done 2026-07-12** — constraint added; both `add_member` and `bulk_add_members` now catch the race (falling back to per-row commits in the bulk case so one conflicting row doesn't lose the rest of a legitimate batch) instead of surfacing a raw 500. Verified live: adding the same member twice is idempotent, no duplicate row.

- ✅ **[Bug]** `AudienceGroupDB.name` uniqueness is case-sensitive and unhandled — "Newsletter VIPs" and "newsletter vips" succeed as two distinct groups, and a genuine duplicate name raises an unhandled 500 instead of a clean error (`router.py:16-18`, `service.py:15-33`). Fix: enforce case-insensitive uniqueness and catch `IntegrityError` to return a clean 409 with a clear message. Source: [[Interview Prep - Content, Campaigns, Audience]] → Audience Q5. **Done 2026-07-12** — replaced the plain case-sensitive `unique=True` with a functional unique index on `lower(name)`; both the API and UI now catch the conflict and return a clean 409 with an error banner instead of a 500. Verified live: `"newsletter vips"` correctly rejected as a duplicate of `"Newsletter VIPs"`.

- ✅ **[Bug]** `create_campaign` (`campaigns/service.py:33-61`) auto-creates the initial `VariantDB` via two independent `db.commit()` calls rather than one transaction — a failure between them (e.g. DB connection drop) leaves a persisted campaign with zero variants, violating the "a campaign always has a variant" invariant. Fix: wrap both inserts in a single transaction (flush + one commit at the end) so it's atomic. Source: [[Interview Prep - Content, Campaigns, Audience]] → Campaigns Q1. **Done 2026-07-12** — `db.flush()` after the campaign insert (assigns the id without ending the transaction), then one `db.commit()` for both rows.

- ✅ **[Bug]** Deleting a category or content record that still has relations (parent/child edges, category assignments) should not silently cascade — raise a confirmation-style error surfacing what it's connected to ("related to N parent(s) / M child(ren) — delete anyway?") so a manager can re-parent/re-assign first if needed. Applies once delete endpoints for content records/categories are built (none exist yet); pairs with the FK/cascade design from Content Q5. Does not cover the harder historical-data question below — see the 📋 Needs ADR item. Source: [[Interview Prep - Content, Campaigns, Audience]] → Content Q6. **Done 2026-07-12** — built `DELETE /content/{id}` and `DELETE /content/categories/{id}` (they didn't exist before this). Split relations into two tiers: decision-resolution/override history is a **hard block**, never force-deletable (consistent with the "never hard-delete anything with historical usage" leaning already in the data-lifecycle Needs-ADR item below — this doesn't build the archive mechanism itself, just refuses to destroy history in the meantime); category assignments, versions, and module instances are **soft/reassignable** — without `force`, a 409 lists counts and asks "delete anyway?"; with `force=true`, they cascade-delete (module instances get `content_record_id` cleared rather than being deleted, so campaign structure survives). Added matching UI: a Delete button on both detail pages, and a "Yes, delete anyway" button that appears once the soft-relations error is shown. Verified live end-to-end via the API (hard block, soft block + counts, force bypass, cascade correctness) and via the actual HTML form-post delete flow.
