## Description

✅ **DECIDED AND ACCEPTED 2026-09-19 — [[ADR-169 — Operational Flows Are Sequenced Variants, Not a Canvas]].** **The React frontend is unblocked**: the largest unknown surface in the manager UI does not exist. A canvas is revisitable under a named two-part trigger — a case per-variant followups cannot express *and* that an orchestrator cannot cover either — which is a narrow intersection and may be empty. **No canvas.** Unsubscribe and double opt-in are routes rather than flows, which dissolves the ADR-142 contradiction instead of resolving it — no flow was ever involved, so the platform staying usable without an orchestrator costs nothing. Multi-step cycles are a sequence of variants with per-variant followup conditions: an adjacency list authored one email at a time rather than a graph drawn from above. The reminder item below collapses into it. The blocked items — the unsubscribe surface, double opt-in, ADR-163's opt-out scope — become buildable as ordinary routes on acceptance. The entry below is the working record the ADR was drafted from and stays until it is accepted. --- **How does this platform express an operational flow at all — a journey builder, or Python written by a developer?** Surfaced 2026-09-15 (user) while deciding consent-by-brand, when the [[ADR-163 — Per-Channel Consent and Addressability]] addendum found there is **no unsubscribe page anywhere** and **no double-opt-in subscription process** — the only opt-out writer is the provider webhook. **The framing matters more than the gap.** The user rejected "we need to build an unsubscribe process" as the wrong question: *"the architectural decision in this is more of a 'how do we build flows and journeys; do we need an automation studio / journey builder like Salesforce or is this a python script' — and not 'we need to build an unsubscription process'."* They also note there will probably be **more than one unsubscribe process**, which is itself evidence that a one-off script is the wrong shape: you do not write the same script four times, you build the thing that expresses them. **The real tension is with [[ADR-142 — Autonomous Workflows and the Automation Boundary]]**, which already drew this boundary from the other side — the platform owns the *action*, the orchestrator owns the *flow*, and there is no custom orchestrator node because the connector IS the documented REST API. A journey builder inside the platform moves flow ownership back in-house, so either an unsubscribe flow is orchestrated externally like everything else, or ADR-142's boundary needs revisiting. **The sentence that cuts hardest is ADR-142's own** (§2, line 61): *"the platform stays fully usable with no orchestrator at all"* — an unsubscribe cannot depend on an orchestrator a self-hosting company never installed, because it is a legal obligation rather than a convenience, which argues the platform needs *something* of its own even if flows in general live outside. **Blocked behind this decision, and none of them should be built as one-offs first:** the unsubscribe surface (several variants), double opt-in at subscription, and the opt-out scope decided 2026-09-15 in ADR-163 — brand-scoped by default with an optional "all brands" — which currently has nowhere to live. **Do not start any of these before the decision.** Explicit instruction, user, 2026-09-15. **Update 2026-09-18 (user) — the premise is challenged, and the bucket splits into four things that do not share an answer.** **(1) Subscribe (DOI) and unsubscribe are "most important of all"** — global plus per channel, though only email needs a page, since a push opt-out belongs to the phone's own settings. Now filed as its own Feature item at the top of that section, because `List-Unsubscribe` being absent blocks the beta's first send regardless of how flows are expressed. **(2) Customer-lifecycle journeys (birthday, first-buyer, winback) — challenged rather than accepted:** *"maybe we should challenge this as 'it's algo and ai triggered, you don't need a journey builder, because you prepare the content and you get approval requests for sends'."* If that holds, a lifecycle journey is not a canvas at all — it is the signal and decision layers choosing the moment, with [[ADR-142 — Autonomous Workflows and the Automation Boundary]] §4's approval surface as the entire UI. **This is the question that gates the React frontend**, not merely one that informs it: a journey canvas is the largest unknown surface in the manager UI, and answering "no canvas" removes it. **(3) Reminder sends** ("if no open/click after X days, send again") are probably **not a journey but an option on the send-preparation screen**, beside scheduling — small, concrete, and the one piece buildable without settling anything else. **(4) Transactional / after-sales** "may not be a journey too" — an email plus an algorithm, triggered from outside, which makes it [[ADR-166 — Inbound Machine Callers Are Authenticated Principals]]'s territory rather than this one's, converging with the transactional-sends item below.

  **Added 2026-09-17 — system mail belongs to this question too, and for a reason that is not obvious.** The sign-in code is the platform's only outbound mail that is not a campaign, and today it goes out through the marketing adapter (`auth/service.py` → `get_provider(system_mail_provider())`). It has never been sent for real: the mock provider writes the code to the server log and that is how the user has been signing in. **The user's framing:** *"sign in emails is not just communication, but data also"* — a sign-in mail is a step in a flow with state (requested, delivered, consumed, expired), which is exactly what a journey expresses and what a one-off `send()` call does not. So if the platform grows any flow machinery of its own, system mail is one of its first tenants, not a separate feature.

  **A deployment detail to record now, though it is not a decision for today:** a real installation uses **separate sending domains for system, transactional and marketing mail** — the user intends a dedicated Resend domain with a system prefix. The reason is already half-written in the code: `auth/service.py` warns that an unset `SYSTEM_MAIL_FROM` means "system mail is going out from the marketing sender, so campaign complaint rates can push sign-in codes into spam and lock operators out". The separation exists so a marketing reputation problem cannot take sign-in down with it. `SYSTEM_MAIL_FROM` and `SYSTEM_MAIL_PROVIDER` already exist as the hooks; nothing more is needed until the flow question is answered. Source: user, 2026-09-17.
