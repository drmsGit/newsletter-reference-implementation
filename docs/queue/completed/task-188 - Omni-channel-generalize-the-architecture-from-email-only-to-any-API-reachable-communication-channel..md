✅ **Omni-channel: generalize the architecture from email-only to any API-reachable communication channel.** Surfaced 2026-08-12 (user). **Full write-up in [[Omni-Channel - design interview]]** — that file holds the analysis, what is already settled, and the planned five-cluster interview; this entry exists so the item is visible to the normal process. **The ask:** content management and orchestration for any channel an adopter can reach — a letter shop, a push service, a messaging platform, a paid-social ad account — not all at once, but with a structure that absorbs new channels cheaply. **Settled up front, not open for the interview:** per-channel variants under a shared campaign; channel selection is the manager's choice and never forced; **organic/broadcast social is out of scope** (the interest is personalized *paid* social — build a target group, hand it to Meta/TikTok, delivered one-to-one); the long-term direction is smaller and smaller groups, down to one-to-one; and the shared core (content, decision, audience, signal, override) stays shared. **Scope is smaller than it sounds:** roughly 80% of the architecture is already channel-neutral — [[ADR-012 — Content Records Represent Communication Units]] deliberately defines a record as a communication unit rather than an email, the decision layer resolves content records and knows nothing about email, and [[ADR-022 — Delivery Type Is Independent From Composition]] plus [[ADR-100 — Provider Layer as Send and Feedback Adapter]]/[[ADR-101 — Provider Capabilities Are Explicit]] already provide the seams. The email binding is concentrated in **five places in one thin band at the outbound end**: the `send(recipient_email, subject, html)` provider signature (`delivery/providers/base.py:15`), `VariantDB.subject`/`preheader` as columns (`campaigns/db_models.py:32`), HTML-only rendering and the `html_*` snapshot columns (`snapshots/db_models.py:12`), the `email_modules` registry, and single-column consent with `email` as the only address (`recipients/db_models.py:11`). **Two sequencing arguments for doing it sooner rather than later, both about avoiding a double build:** (1) **it overlaps the open P0 consent bug** — per-channel consent restructures the same send-time gate the P0 fix has to touch, so running Cluster 4 first means fixing it once in the right shape; (2) **the React/Node frontend has not started**, so doing this first lets the manager UI be designed against channel-shaped variants instead of retrofitting a second codebase. **Known hard constraint worth recording now:** on paid social the identifiers go one-way (hashed, never matched back), match rates are partial, ad platforms enforce **minimum audience sizes** — so one-to-one works on email/push/SMS/letter but **not** on paid social — and feedback arrives **aggregate per audience+creative**, which must not be attributed down to individuals or it corrupts the per-recipient signal layer. Consent there is also per-channel *and purpose* ("may I email you" ≠ "may I upload your hashed address to an ad platform"); German DPAs have taken a restrictive line on customer-list uploads, to be verified with counsel rather than by us, consistent with the [[ADR-144 — AI Data and Model Governance]] stance of staying out of the legal determination. **Also touches naming:** [[ADR-001 — Newsletter Architecture Boundaries]] scopes the core to "newsletter-specific responsibilities" and would need a superseding boundary ADR. Expected output: roughly a 160-block of ADRs. **Interview deferred by the user 2026-08-12; no code changes until it runs.** Source: user, 2026-08-12 (omni-channel direction session). **DESIGN RESOLVED 2026-09-12** — the interview closed 2026-09-01 (25/25) and is written up as [[ADR-160 — Channel Model and Composition]], [[ADR-161 — Channel Execution Shapes]], [[ADR-162 — Channel Rendering and Artifacts]], [[ADR-163 — Per-Channel Consent and Addressability]] and [[ADR-164 — Channel Feedback and Signals]], all accepted 2026-09-12, plus [[ADR-165 — Core Scope Is Channel-Neutral Content Orchestration]] which **supersedes ADR-001** (the repo's first supersession) and answers the naming question above. Seven dated addenda were written to ADR-021/062/063/101/103/121/122. The three decisions the interview left open are also closed: unlicensed-channel disable via a settings-row toggle (ADR-160 §8), address-pick via an optional `is_primary` flag with most-recently-verified fallback (ADR-163 §11), and ADR-001's fate. **Nothing is built.** What remains is implementation, not design — the migrations (consent events + addressability, `html_*`→`artifact_*`, subject/preheader into module fields, `SignalContributionDB.channel`, delivery transfer rows) are not yet broken out as individual 🔴 items; that sequencing is the open Cowork timeline pass. Keeping this entry 📋 would now be wrong — it is no longer blocked on a design decision.
