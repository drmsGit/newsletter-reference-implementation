📋 **[Needs design] — the frontend is being built from the API surface, and nothing records what a manager actually does.** Raised by the user 2026-09-20, mid-build: *"I build the backend as the structure how the final results are stored … But no documents show WHAT and WHY I want to do (in an operative way) … it feels like you assume a lot and that way I can't review if you're adding unnecessary code that bloats the software."* **Full write-up in [[Manager Workflow - design interview]]** — this entry exists so the item is visible to the normal process. **The gap is real and documented:** `docs/react-screen-inventory.md` opens by saying it is *"an inventory, not a design … it does not say what any of it should look like, how it should be laid out, or what should be on one page versus two — those are the design pass's questions and this document deliberately leaves them open."* Two phases of client were built anyway. The ADRs record what is possible and forbidden; the services record how results are stored so any caller can produce them; **neither records what the work is.** **What was guessed rather than decided**, and is in scope to overturn: approvals as the landing screen, the three columns on every list, campaign rows not navigating, and content fields rendered as one flat list with email and push interleaved in JSON insertion order — the last being what the user objected to. **INTERVIEW CLOSED 2026-09-24 — all five clusters, 52 of 53 answered**; only Cluster 1 question 5 stays open, reopened at the user's request. **CLUSTER 5 CLOSED 8/8:** the send review screen blocks what is broken and reports what is merely questionable, which is the narrow exception to *the system reports, the manager decides*; **always recalculate before sending**, so `freeze` becomes the mode that should never be used although both the function and column default to it; scheduling is one mechanism for managers and automations alike, since an automation can express immediacy as *now + 5 minutes*; monitoring and deliveries are two screens, not one, which also answers Q3.1b; and a failed send needs **no retry feature** — build a segment of who missed it. **Three more gaps (running total eighteen):** audience criteria cannot express delivery history, since all four keys are recipient attributes while *"campaign X was or was not delivered"* queries `DeliveryExecutionDB`; **nothing prevents self-approval**, because `may_decide` never compares decider to requester — safe only while machines requested and could not approve, and a hole the moment Q5.8 lets a person request; and no route answers "which campaigns are in flight". **A pattern named rather than three accidents:** response models routinely expose less than their tables store — `ModuleVariableOut`, `PendingActionDetail` and `SendInstance` all drop fields a screen needs. Worth a sweep; Phase 0's schema-honesty pass caught bare dicts and missed under-exposure. **The first cut is nineteen screens, not sixteen** — decision history, the variant editor and monitoring were each added because a screen was being asked to answer two questions. **Next:** the ADRs this owes, and the variant editor's own design interview. **CLUSTER 4 CLOSED 2026-09-24, 7/7**, and it **reverses a dated decision**. `resolve_audience` implements `((∪ include) − (∪ exclude)) ∪ pins`, its docstring recording from 2026-07-26 that *"a manual pin is always included — exclude blocks never remove a hand-pinned recipient"*. That is now wrong: **exclusion segments beat a force-add**, governed by a principle worth more than the case — *"shouldn't get it by human beats should get it by system/human"*, because wrongly including costs more than wrongly omitting. The consent/suppression floor is untouched and stays absolute. **The old decision is in a docstring and four doc pages, not an ADR**, so this is no supersession — but it is a deliberate reversal and should get a record. Tests assert pins against the consent floor only, so the blast radius is smaller than the document count suggests. It also needs a distinction the model lacks: an **exclusion segment** is editorial (attribute, topic, interest, temporary), a **blocklist** is legal and data-protection, and both are `kind="exclude"` today. **Four more backend gaps (running total fifteen):** no JSON route for audience suggestion, although Q4.1 makes suggestion the *primary* way an audience comes into being and all four service functions exist Jinja-only; `resolve_audience` returns only the final list and discards the arithmetic it already computed, which Q4.3 says is exactly what a manager must see; **no per-recipient delivery query and no reverse membership lookup** — the second being structural rather than missing, since rule-based membership is computed at resolution time and never stored, so only pins are rows and "which groups is Anna in" needs every group resolved; and `resolve_audience` defaults `channel` to email, which Q4.4 rules always wrong on screen and which the docstring records as having once made a push send resolve to nobody. **Recipients is temporary by design** — read-only, existing only because the reasoning lives here rather than in the CRM, and going away when the CRM can receive it. That bounds the investment. **CLUSTER 3 CLOSED 2026-09-23, 10/10**, and its largest finding is an absence: *"in the backend process the real editor was never discussed."* A manager will not compose by selecting content from one dropdown and a layout from another — what is needed is live rendering of the chosen blocks, module ordering, direct field editing rather than JSON, and element hiding. **That editor appears in no inventory**, it is where the weight of composing actually sits, and it gets **its own design interview**, which does not depend on Clusters 4 or 5. Its beta priority is the seam rather than the editor: *"concept is the most important to find a way that companies can easily customize their frontend editor functions as the need it and how their managers work best"*. **Three more backend gaps (running total eleven):** no distribution endpoint for a decision slot, where the answer is an aggregate over `DecisionResolutionDB` grouped by content record; **`GET /campaigns/decision-slots/{id}/resolutions` returns every row unpaginated** on the table its own comment calls the fastest-growing in the schema at 96,040 rows, which is the worst instance of what Q2.10 ruled against; and `duplicate_campaign` cannot accept a facet-value mapping, which Q2.9b's per-brand decision requires. **A capability with no model:** hiding an element. `ModuleInstanceDB` has no visibility flag, and ADR-086's hidden slot is automatic degradation rather than a manager's choice. **The second structural principle was named here — a screen answers one question** — arrived at independently three times: no dashboard, history out of the inbox, monitoring out of the campaign list. **CLUSTER 1 ◐ 7/8 CLOSED 2026-09-23**, question 5 reopened at the user's request. It stated this product's thesis for the first time — *"this is a future platform, there will be more ai and more decisions to make"* — so **the manager's job is shifting from producing to deciding**, which confirms the approval inbox as the landing screen and rejects a dashboard on evidence. That is a positioning statement as much as a design one and bears on the open POSITIONING gate. **Three more backend gaps:** `PendingActionDetail` does not expose `subject_type`/`subject_id` although the table stores both, so the client cannot link to the thing being decided (second instance of a response model dropping fields the table has); `GET /approvals/` accepts only `status`, with no action-type filter, requester filter or paging; and **a held action cannot exist without a deadline** — `expires_at` is `nullable=False` and `default_ttl_seconds: int` is not optional, so "content review does not expire" needs a schema change, a hand-written migration, and every comparison to read null as *never expires*. **And one that belongs to Cluster 4:** audience membership records no reason, and the case needing one is external automation — an orchestrator selecting recipients daily must say *why this recipient*, which the platform cannot reconstruct when the rule is AI-driven. `POST /api/audience-groups/{id}/members/{id}` takes no request body at all. **The first cut grew to seventeen screens** — decision history separates from the inbox, keeping log and queue apart. **CLUSTER 2 CLOSED 2026-09-21, 18/18.** It produced five backend requirements that did not exist before it ran — a required-field check before a send fires (nothing checks today, so an empty push ships to a real device); a read-only decision-slot candidate count (`execute` resolves for real and writes a `DecisionResolution`, so a slot cannot be previewed); a content-readiness approvable action plus its `APPROVABLE_ROUTES` entry (fail-closed by omission, so a machine would get a hard 403 rather than a hold); the **facet** model — declared facets, values, and links from content and campaigns, per brand, governed in Settings, which inherits gap C2; and server-side filtering plus pagination on every list route, which reprices P3-02 from a latent scaling note to a blocker. **ADR work owed:** a dated addendum to [[ADR-161 — Channel Execution Shapes]] point 7, whose rider *"catalogue readiness is 'push fields not empty'"* is now false since readiness is asserted rather than computed; a sentence in [[ADR-150 — Tenancy and Access Model]]'s addendum on why findability differs from affinity, so facets are per-brand while categories stay global; and a record of its own for facets, which are a new first-class concept. **It also invalidates part of Phase 2** — the flat content-field list is wrong, and the four list screens fetch everything and render it, which will not survive server-side paging. That is the cost of having built them before the interview ran. **Structure:** five clusters over the sixteen first-cut screens, following [[Omni-Channel - design interview]], which closed 25/25 and produced the 160-block. **Clustering approved 2026-09-21 and all five clusters written out — 41 questions, 1 resolved.** Q2.7 closed the same day: categories are authored alongside content, not in the campaign context, so they stay in the authoring cluster. **The parked backend conflict is resolved, 2026-09-21, and it resolved toward the ADRs.** The user, after sleeping on it: *"There is no case that a content field on a content exists BEFORE there is a module/layout. So grouping UI based on the module channels will be fine."* So [[ADR-161 — Channel Execution Shapes]] point 7 holds as written and [[ADR-162 — Channel Rendering and Artifacts]] point 1 is not violated — **no ADR is needed and none should be written.** What follows is maintenance rather than design: `CONTENT_FIELD_GROUPS` (`backend/app/content/service.py:101-108`) should read from the manifests instead of repeating them, which is exactly what its own docstring asks for, and the duplicate email list at `backend/scripts/import_content_csv.py:33-41` goes with it. **A genuinely new requirement came out of the same message and is NOT covered by that**, now questions 2.8–2.14: **content findability at scale**. Clarified by the user 2026-09-21: *"CategoryDB and the whole 'categorize content' is ONLY meant for the 'build a dynamic affinities profile of each recipient'"* — consistent with [[ADR-080 — Human-governed Taxonomy Before AI Selection]], which makes categories the governed taxonomy for content *selection* and says nothing about finding anything. What is missing is the manager's own grouping, for finding a record among many: *"this could be a filter to distinguish b2c / b2b content, or to match content to IATA destinations or countries or regions, or to separate product from company information … Only they can decide how they typically group content."* Proposed word: **tags**, since "category" is taken. **The boundary is the load-bearing part:** if such a label can reach the decision engine it *is* a category and ADR-080 governs it; if it must never, the separation has to be structural rather than conventional — nothing stops somebody reusing `CategoryDB` today, and a manager tagging content "B2B" there would silently make "B2B" an affinity dimension. **Two surfaces:** the content table, and the campaign builder, which is *"a dropdown with all content record ids"* today. **And one constraint that may outrank tags entirely:** `GET /content/` calls `.all()` with no limit, offset or filter, and so does every other list route the client uses (`content/service.py:219-235`). At the scale described this is not a performance note — the screen stops working. Already logged as P3-02 from the 2026-08-07 review, where it was scoped as latent scaling rather than as a blocker on the core workflow; question 2.10 is what reprices it.
