# Interview Prep — AI Layer

Generated 2026-08-02 via `/interview-prep`, for the `backend/app/ai/` feature: the `AIProvider` contract, the real Claude adapter, the token-based pre-call spend gate, cost accounting, prompt versioning, and the first Mode-A task (subject/preheader). Focus: why-this-over-the-alternative, edge cases / failure modes, performance / concurrency. Companion business-classification in `docs/business-interview.md` (same date). Check off each item once discussed, and record any decision in **Resolution**.

## AI Layer

- [x] **Q1.** Why enforce the spend cap as a *pre-call* token gate instead of tracking spend after each call and stopping when you cross the line?
    **A:** A post-hoc ledger only tells you you've *already* overspent — the overage is the run that crossed the line. The design makes the worst case knowable before spending: `count_input_tokens() + max_output_tokens` (`service.py:187`), refused if it doesn't fit the remaining cap. A stop always lands *between* runs, never mid-run, and nothing is spent on work that can't finish (`service.py:1-14`). The cost is a second network round-trip (the count call) before every generate — deliberately paid because the alternative is a cap that only enforces after the money's gone.
    **Resolution:** Keep in project — this is ADR-144 §5 implemented as designed, not an accident of implementation. The extra round-trip is the accepted price of a cap that enforces before the money is spent, and the behaviour is verified (a refused run left the ledger at exactly 0).

- [x] **Q2.** `count_input_tokens` is a required abstract method, not optional. Why bake it into the contract rather than treat it as a nice-to-have?
    **A:** The cap is only real if every model behind the contract can be gated. An adapter that can't count can't compute a worst case, so it can't participate in the pre-call gate — making it optional would mean some models silently bypass the cap (`base.py:57-71`). This is the ADR-101 "capabilities are explicit" posture: the gate is a property of the contract, not of whichever vendor happens to support it.
    **Resolution:** Keep in project — the requirement stands. A model sold in the EU that cannot report what a call cost is considered very unlikely, so the contract is not going to block a realistic adapter. It remains *possible* though, and a company hitting it must not be stuck: logged as a documented escape hatch — how to add an adapter whose vendor has no counting endpoint, and what you give up (the pre-call gate) by doing so. See the backlog Feature; this is a structural/documentation gap, not a change to the contract.

- [x] **Q3.** When token counting fails, you refuse the run rather than fall back to a word-count estimate. Isn't refusing worse UX than proceeding on an approximation?
    **A:** An estimate-based gate isn't a gate — it lets a run start against a number nobody verified (`base.py:13-21`). `TokenCountUnavailable` is raised and the run is recorded `blocked` with "Nothing was spent" (`service.py:171-185`). The failure mode this protects against: a network blip on the cheap count endpoint quietly disabling the cap on the expensive generate endpoint. Refusing is both the conservative branch and the honest one — and it's auditable, so the manager sees *why*.
    **Resolution:** Keep in project. Refusing over estimating stands; the behaviour proved its worth on 2026-08-02, when the refusal message ("the cost of this run could not be verified up front — ANTHROPIC_API_KEY is not set. Nothing was spent.") is what made a misconfiguration diagnosable instead of a dead button. **Retry/recovery UX is deferred to a future discussion, ideally informed by UAT**, and is not treated as a gap now: the realistic flow is *manager clicks run → no tokens → escalates → budget approved* — and budget approval is a "starting next month" event, not a "do it now" one, since most companies run a spending cap distributed across departments. So a fast retry path buys little. The one case worth revisiting later is **recovery cost by task type**: re-clicking for a subject line is trivial, but losing complex AI settings or a long prompt that took real work to build is not — the answer will depend on the task, not on the gate.

- [x] **Q4.** The biggest failure mode: `tokens_used()` reads the ledger, the gate checks it, then `generate()` runs — but two concurrent runs can both pass the gate. Is the cap actually enforced under concurrency?
    **A:** No — a genuine TOCTOU gap. `tokens_used()` sums the table (`service.py:89-104`), the gate compares against it (`service.py:193`), but there's no lock or reservation between the check and the `_record()` of the resulting run. Two requests reading the same "remaining" both proceed, and the cap can be overshot by up to one concurrent batch's worst case. Unlike `send_send_instance` (which uses `with_for_update()` on the status transition), there's no equivalent serialization here. Tolerable at single-operator/few-runs scale; the first thing that breaks if AI runs fan out. Same systemic concurrency gap already flagged in the backlog for override/double-send races.
    **Resolution:** Act/fix — but **not as an AI-layer fix**. The user reframed it as a general architectural question the project has never answered: *what happens when two people or systems do the same thing at the same time* — two managers in one campaign, both clicking send, a report running mid-edit. Three sub-problems, only one of which is locking: **(a)** human ↔ human presence/locking with an unlock path and conflict detection; **(b)** a **precedence policy that AI stands back when a real person is working on something** — a governance rule, not a database mechanism; **(c)** a queue carrying a log, so an action that never fired or failed still records when and why. The pre-existing Features item ("systemic pattern for concurrency guards", scoped to write-endpoint races) was **superseded and promoted to Needs ADR** with this broader framing, absorbing all three known instances: override outcome-delta, delivery double-send, and this cap TOCTOU. Fixing the AI instance alone was explicitly rejected — the project already has one ad-hoc answer (`with_for_update()` in `send_send_instance`) and no convention, and adding a second would deepen exactly the problem. Blast radius here is bounded (~one racing run's worst case, about a cent), so it is not urgent on its own; it is urgent as the third instance, and because AI runs are the most likely thing to actually go concurrent first.

- [x] **Q5.** `tokens_used()` re-sums the entire `ai_runs` table on every single run. Performance concern?
    **A:** Yes, latent. It's a full-table scan filtered in Python (`is_billable` isn't a simple WHERE since "free" is a provider set), run once per task (`service.py:97-104`). Negligible now, O(all runs ever) as the ledger grows — and it's on the hot path *before* every call, so every AI run gets slower as history accumulates. Deferrable fixes: a running counter, a windowed sum, or a SQL `SUM` with a provider filter.
    **Resolution:** Act/fix, at low priority. Correction to the baseline answer: it is now **two** full scans, not one — `spend_to_date()` (added 2026-08-02 for the USD display) walks the same table again, so the Settings page and every gated run each pay twice. Urgency is genuinely low: the table holds 20 rows, and even at ~1,000 runs a month it is low tens of thousands of rows a year, summed in milliseconds against a network call that takes seconds. Agreed fix is the cheap one — push the provider filter into SQL (`SUM` with `WHERE provider NOT IN (...)`) rather than pulling rows into Python — because it needs no counter and no cache that can go stale. The user also proposed a **separate performance-notes document** as the home for this class of latent, not-yet-urgent finding; logged in the backlog.

- [x] **Q6.** Billability defaults to "billable" but cost defaults to "unknown/zero-contribution." Those are opposite defaults — why not make them consistent?
    **A:** They answer opposite-risk questions (`pricing.py:9-19`). For the *cap*, the safe error is to over-count: a paid adapter someone forgot to price still burns budget (`is_billable` returns True for anything not named free), so the gate degrades conservative, never permissive. For the *money display*, the safe error is to *not* invent a number: an unpriced model contributes nothing to the USD total and is surfaced as `unpriced_runs` (`service.py:107-133`), because silently pricing it at zero would show a manager a total wrong in the direction that matters. Same-direction defaults would get one of the two wrong.
    **Resolution:** Keep in poc. The opposite defaults stand — they are correct for their respective risks. The weakness the question does *not* raise is accepted for now: `MODEL_PRICING` is hand-maintained with a "verified" date and nothing detects staleness, so a vendor price change would leave the code confidently computing a wrong total — an *unknown* model is loudly unpriced, but a *stale* price is silently wrong. Acceptable in the POC, where an admin maintains the number and the budget in Settings. **The future direction dissolves the problem rather than patching it:** a company's AI budget is company-wide, and this platform will not be its only token consumer, so the remaining budget should be **read from the company's AI source** rather than configured locally — at which point our table stops being the authority and cannot go stale. Logged as a documentation/direction item in the backlog.

- [x] **Q7.** Extended thinking is off by default. Preference or correctness?
    **A:** Correctness-of-cost. `max_tokens` is a ceiling on thinking *plus* reply, so on a task declaring a 400-token output ceiling the model could burn the whole budget reasoning and return a truncated answer (`claude.py:89-96`). With thinking off, the ceiling means what the task intended and the worst-case arithmetic the gate relies on stays tight. A task that genuinely needs reasoning turns it on *and* raises its own ceiling to match — the two must move together.
    **Resolution:** Act/fix. The reasoning stands; the gap is that *"the two must move together"* is asserted in a comment and **enforced by nothing**. `thinking` is set on the adapter constructor and `max_output_tokens` in the task file — two different places, no check between them — so the first task that enables reasoning and leaves its ceiling at 400 silently reintroduces exactly the truncation the default was chosen to prevent. Latent rather than live (nothing enables thinking today). Agreed fix is a **floor**: refuse or warn when thinking is on and the declared ceiling is below a sane minimum. **User's calibration for this whole area, recorded because it should shape the fix:** the warn/hard-stop pair already exists, and today most companies simply notice they ran out of tokens. This does not need to be inventive, original or perfect, and can adapt over time — its only job is to buy a **reasonable amount of time** while automations are running, so someone gets a notification, escalates and obtains more budget before the next big prompt lands. Keep the guard simple.

- [x] **Q8.** A model refusal comes back as HTTP 200 with empty content, and `max_tokens` truncation comes back as apparent success. How are these kept from looking like normal output?
    **A:** Both handled off `stop_reason`, not status code. A `refusal` at HTTP 200 is mapped to `success=False` with a reason (`claude.py:175-192`) — otherwise the UI shows an empty box and reads it as a formatting bug. A `max_tokens` stop is returned to the caller as a *partial* (ADR-144: showing isn't committing) but the audit row records "output hit its ceiling and is truncated" (`service.py:223-227`). And `parse_options` is deliberately tolerant — a model that drifts from the requested layout degrades to fewer options, never an exception in the request path (`subject_preheader.py:74-98`).
    **Resolution:** Act/fix — the *handling* is correct and proven (the 2026-08-02 truncated run was flagged in the audit row and still surfaced its options), but the **display end drops the information**. Two gaps, both one layer above the paths this answer describes. **(1)** The audit row records "output hit its ceiling and is truncated" and the campaign page never shows it — the manager sees three suggestions and no sign the third may be cut off mid-sentence, then applies one to a real campaign. The system knows and does not say. **(2)** Tolerant parsing degrades silently: if two well-formed options come back instead of three, the manager gets two and nothing indicates one was lost. Degrading beats raising, but it should be observable. Logged as a Bug (low severity) rather than a Feature, because in both cases the information already exists and is withheld from the person acting on it.

## Cross-cutting note

The standout finding is **Q4 — the cap's check-then-act race**, the one place the "the cap is a real gate" claim has a hole under concurrency. It shares a root cause with the existing systemic concurrency-guard item in `docs/backlog.md` (override outcome-delta race, delivery double-send race).
